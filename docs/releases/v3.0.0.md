Specus v3.0.0 是 v1.2.6 之后的第一个正式版本，包含此后合入 main 的全部改动。原计划的 v1.2.7 没有发布，它的出口分流一期内容并入本版；版本号从 1.2 直接升到 3.0，没有 2.x 版本。本版的主体是 Peer 出口分流（IPv4/IPv6 地址与网段、域名规则与系统 DNS 接管）、四个界面统一改版、服务工作台与 HTTP 发布相关的新能力，以及一批 Peer Mesh、账号授权与数据库修复。控制协议仍为 v2，帧格式不变；需要两端都升级的能力见「升级说明」。

## 界面全新设计

- 四个界面改用同一套设计：浅色毛玻璃材质、唯一的系统蓝强调色、大圆角、胶囊式标签页与状态标签、系统字体，支持浅色与深色。
- 管理后台及其公开页面（互传、客户端下载、NAT 检测、登录落地页）：悬浮玻璃侧栏，每个面板以 30px 页头开始，表单标签放在输入框上方，提示改为深色玻璃浮层；菜单里的 emoji 换成线条图标。
- CLI 本地管理页（Go、Java、.NET 共用同一份页面）：新的玻璃侧栏、卡片与分段控件，跟随系统深色模式；768px 以下改为顶部标签栏。页面行为与 CSP 不变。
- Windows 桌面客户端（WPF）与 Android 客户端按同一套设计令牌改换样式与布局，功能与绑定不变：WPF 改为悬浮侧栏、胶囊页签与卡片，保留原有的深浅主题切换（玻璃只是半透明色，没有背景模糊）；Android 改为卡片、胶囊分段切换与状态标签，跟随系统深色模式。
- 去掉内置的 Inter 字体，改用系统字体栈。各端令牌的位置与改界面时的规则见 [界面设计系统](../architecture/ui-design-system.md)。

## Peer 出口分流

- 消费端按规则把指定目标的流量经已授权的对端设备（出口）访问，应用无需逐个配置代理；未命中规则的流量照常从本机出去。Java、Go、.NET 客户端都可作为消费端与出口；消费端支持 Linux、Windows、macOS，Android 不提供出口分流。关联 #42。
- 规则写在客户端配置的 `peerEgressRules`，三端共用；动作分 `egress`、`direct`、`block`，前缀更长者优先，单条规则可停用。保存规则与启用接管分开：总开关 `peerEgressEnabled` 默认 `false`，关闭时规则只保存、不接管，`config validate`、启动日志与状态都会明确提示。
- 出口由服务端租户总开关与每台设备的出口策略共同控制，目的规则默认全部拒绝，并与基础 Peer ACL 取交集；回环、链路本地与云元数据、组播广播、组网网段与本部署的控制端点永远拒绝。服务端保存策略时按出口的读法校验目的规则（#99），策略变更立即推送给在线设备。
- 命中规则而出口不可用时阻断，不回退到本机直连：TCP 立即复位，UDP 收到主机不可达，已建立的连接在出口离线或规则改动时被复位。出口未被提供给本机、对端运行的客户端不支持出口时同样阻断并说明原因；服务端不下发出口目录时提示服务端可能过旧（#121）。
- 路由接管只写运行期路由表（Linux `ip route`，Windows ActiveStore，macOS `route`，重启后不存在），不改防火墙与内核转发参数；只装精确前缀，前缀已被占用时拒绝并报告占用者，不抢占。虚拟网卡就绪后才应用，每 5 秒按对端、中继与控制连接重算，并对照真实路由表补回消失或指错的条目；控制连接断开只挂起，不撤路由、不关网卡，真正退出时才撤回；崩溃留下的路由在下次启动时按安装记录收回。
- 出口用用户态连接栈终结连接、用普通 socket 连接目标，不做内核转发；Windows 与 macOS 上出站 socket 绑定到隧道之外的接口，Linux 上打 `SO_MARK 0x5350`。
- 出口到消费端方向遵守消费端通告的接收窗口，每流有发送预算，并对目标 socket 施加背压，大响应完整送达（#74）；租户开关关闭等撤权后，已建立的流立即被切断（#75）；RTT 取样按 Karn 规则，丢包时不会长时间停滞（#108）；消费端立即复用刚关闭连接的源端口时，新连接不必等 SYN 重传（#256）。
- 出口按消费设备限制新建流速率（可突发 128 条，之后每秒 64 条，#119），并向服务端上报计数（#125）；消费端流表有界，结束或空闲的流会被回收（#102）。
- 管理入口：管理后台「私有组网 → 出口分流」页（总开关、出口策略与活动，#97）；Windows 桌面端「出口分流」页（规则、接管开关、按配置预演与连通测试、运行状态，#96）；CLI `egress`、`egress rules|rule …`、`egress enable|disable`、`egress test`，以及本地管理页的「出口规则」页与出口状态面板（#98）。
- 使用与排查见 [出口分流使用说明](../peer-mesh/peer-egress-usage.md)，线协议见 [peer-egress.md](../../protocol/spec/peer-egress.md)。

## 出口分流：域名规则与系统 DNS 接管

- 打开 `peerEgressDnsTakeover`（默认关闭，需同时打开 `peerEgressEnabled`）后，规则可写精确域名或 `*.example.com`。命中的查询由消费端用 fake-IP 应答（默认池 `198.18.0.0/15`），流量到达时把域名交给出口，由出口在自己的网络里解析、授权并连接。不打开时域名规则照旧被拒绝，不会在启动时解析成 IP。
- 出口策略新增按名字授权的 `domainRules`（#126）。出口解析出的地址仍要过永远拒绝清单与目标范围，解析到元数据或内网地址的名字照样被拒。
- 这是整个功能里唯一修改系统设置的部分：Linux 经 systemd-resolved 或改写 `/etc/resolv.conf`，macOS 用 `networksetup`，Windows 添加一条 NRPT 规则。改动前写事务日志 `~/.specus/egress-dns-journal.json`，退出时改回，被强杀后在下次启动或执行 `egress dns restore` 时回滚。开关与状态用 `egress dns enable|disable|status|restore`。
- 可识别边界：应用自带 DoH/DoT、使用系统缓存或直接硬编码 IP 时，域名规则不会命中，这类流量只能靠 IP/CIDR 规则覆盖。规范见 [peer-egress-dns.md](../../protocol/spec/peer-egress-dns.md)。

## 出口分流：IPv6

- 消费端规则与出口策略的目的规则都可写 IPv6 地址与前缀，服务端按 RFC 5952 规范形式保存（#243）；名字没有 A 记录时出口按 AAAA 记录拨号（#244）。
- 三个客户端都实现了消费端 IPv6 数据面（#245）：设备的 IPv6 地址由组网 IPv4 推出（`fd53:7065:6375:7300::/96`），IPv6 包原样经 SPEG1 交给声明了 `ipv6PacketCapable` 的出口；路由接管、旁路、漂移修复与明确失败按地址族分开进行，`egress test` 接受 IPv6 地址。
- `peerMeshMtu` 低于 1280 或设备地址没能配到虚拟网卡上时没有 IPv6 数据面，IPv6 规则以 `EGRESS_RULE_IPV6_UNSUPPORTED` 不生效，IPv4 不受影响。fake-IP 的 DNS 应答对 AAAA 仍回 NODATA；组网设备之间仍只走 IPv4。

## Peer 组网修复

- Go 与 .NET 服务端此前转发信令时丢掉 `sourceKeyEpoch`：经这两个服务端的任意两台设备能建立会话、探通直连路径，但数据一个字节都过不去。Java 与 C 服务端不受影响（#72）。
- Go 客户端在 Linux 上此前读不到虚拟网卡的任何数据包（网卡显示 UP 但不交付）；.NET 客户端在 Linux 上释放后立即重建同名网卡偶发 `EBUSY`（#72）。
- 四个服务端在设备离线后向同租户对端推送花名册；Go 与 .NET 服务端不再因信令投递不到而断开发送方的控制连接（#72、#169）。
- Go、Java、.NET、Android：对端重启后忘掉旧路径，改用新进程的地址；直连健康时不再因中继探测在两条路径之间来回切换。Go 客户端在组网未运行时收到会话信令不再崩溃（#136）。

## 服务工作台与 HTTP 发布

以下各项来自 #38，各有独立契约，四个服务端（Java、Go、.NET、C）与管理后台都已实现：

- 服务工作台（#143）：常用服务、最近打开与由现有列表推导的待处理问题，按登录身份保存在服务端；管理后台登录后默认进入工作台。
- 服务连通性检查（#135、#140）：对单条 HTTP route 显式发起一次有界检查，按「已配置 → 设备在线 → 目标可达 → 访问成功」逐段给出结果码；不带凭据、不读响应体、不写流量明细，并有限流。见 [service-connectivity-check.md](../../protocol/spec/service-connectivity-check.md)。
- 临时 HTTP 分享（#144）：为受 Basic 保护的 route 签发有效期必填、可撤销、带审计的访问链接，走独立的 `/http-share/{shareId}/` 路径；默认只读，令牌只存哈希，撤销后下一次请求返回 410，在途流约 2 秒内被切断。
- 产品指标（#146）：默认关闭，由租户管理员确认说明后开启；只记录接入里程碑与互传结果的按日汇总计数，不采集凭证、文件名、文本内容或内网地址，按日计数保留 180 天，可随时清除；运营方可用部署级开关整体禁用。

## 浏览器互传

- 两个浏览器页面之间的直连文件传输支持分块续传（#142）：1 MiB 分块逐块 SHA-256 校验，断线后在会话内续传，重复块幂等。接收方选择写入本机存储时，刷新页面后也能续传，单文件上限 2 GiB；只在内存中接收时仍为 128 MiB。发送方刷新后需要重新选择同一文件，内容变化时停止。
- 四个服务端为 `/transfer`、`/download`、`/nat-detect`、`/diagram`、`/diagram-embed` 提供直接入口，刷新页面或打开带参数的邀请链接不再失效（#288）。

## 账号、授权与安全修复

- HTTP route 公网入口在没有服务端记录、route 已停用或客户端已停用时一律返回 404（四端，#137）；删除或停用 route、停用/改名/删除客户端之后，客户端可靠地停止转发，服务端断开被停用、改名或删除的客户端的连接（#165）。规则见 [http-route.md](../../protocol/spec/http-route.md)。
- 客户端 token 只登录签发它的账户：Go 与 C 服务端此前按名字解析，客户端被删除后新建同名客户端，旧机器会以新账户身份登录（#178）。
- 管理账号（[management-accounts.md](../../protocol/spec/management-accounts.md)）：Go、.NET、C 的登录名改为按租户唯一，与 Java 一致（#198）；token 带账号键 `uid`，删除后重建同名账号不会继承旧 token，删除账号时释放其邮箱（#223）并处理其名下数据（#235）；账号停用、角色变化或删除时撤销其管理 WebSocket（#249）。
- 公网 502 不再回显客户端 RST 的 reason，其中可能含内网地址（#130）；C 服务端管理用户的修改与删除限定在调用者租户内（#139）；并发创建分享不再突破每条 route 的数量上限（#150）。
- 依赖：Spring Boot 4.1.1（Spring Framework 7.0.9，#221）、jackson-databind 2.21.7 / 3.1.7（#106）、.NET 服务端固定 `System.Security.Cryptography.Pkcs` 10.0.13（CVE-2026-84008，#284）、Go 模块强制使用已修补的工具链（#271），以及前端 npm 补丁（#288）。

## 服务端对齐与稳定性

- 控制协议：修正 Go、.NET、C 服务端登录前后的顺序竞态（#164、#170、#179、#188）；一帧写失败或中途被取消后关闭连接，不再在半帧之后继续写（#247）；会让单条 `NAT_CONTROL` 超过 1 MiB 的映射或 route 在创建、启用时以 400 拒绝，写失败的手动下发按离线返回 409（#208、#231、#239）；四个服务端与 Java、Go、.NET 客户端按 RFC 8259 严格读取 NAT 元数据（#350）。
- Direct HTTP / WebSocket：Java 服务端 route WebSocket 的浏览器消息上限从 8 KiB 提到 16 MiB；浏览器不发 CLOSE 就断开时，Java 与 Go 服务端复位设备侧的流（#337、#338、#349）；.NET 服务端队列满或收到迟到帧时只重置该 HTTP 流（#175）；连通性检查不再断开设备的数据连接（#149）。
- 客户端数据连接：Java 客户端遇到慢上游、或一条流连不上本地目标时，不再影响整条数据连接（#82、#129）；.NET 客户端 NAT 流从等待转为活动时不再丢流或乱序（#78）；Android 修正 Direct HTTP 响应尾部与 FIN 丢失、流关闭竞态与桥接 I/O 问题（#230、#252、#269、#291）。
- 数据库：Java 服务端修正 SQLite 约束异常与 BLOB 读取、PostgreSQL 迁移与 HTTP 明细列类型、MySQL/MariaDB 行宽与 LOB 列类型；.NET 服务端修正 MySQL、MariaDB、PostgreSQL 的初始化与迁移（#278、#280、#282），CI 用真实的 MySQL、MariaDB、PostgreSQL 测试；Go 服务端按 Java 的方式保存并展示 HTTP body（#210）；.NET 与 C 服务端给已存在的 Elasticsearch 索引补上 binary body 映射（#204、#215）。
- CLI：状态文件写入失败后每秒重试，不再永久停止发布（#109）；Go 客户端在 Windows 上改用 ACL API 检查文件私有性，不再每秒启动 PowerShell（#95）。

## C 服务端（实验性）

- 继续按 Java 全量对齐（#35）：OIDC 用 JWKS 校验 ID Token 并签发本地 token（#145），客户端登录 nonce 防重放与登录响应 `nettyTls`（#133），Direct WebSocket 完整 SWS2 状态机（#122），以及 NAT 流语义、媒体采集、互传、Peer Mesh 与 TURN、管理 API 清单的逐项对齐。
- 新增 Redis 经 TLS（`rediss://`）与 Sentinel 的协调（#341）、`/actuator/metrics`（#342）、控制连接频率限制（#348）。Java、Go、.NET、Android 客户端经 C 服务端的端到端测试已进入 CI。
- #35 仍未完成，C 服务端不作为 Java 服务端的完整替代。

## 升级说明

- 出口分流需要服务端与消费端、出口两侧的客户端都升级到本版。旧客户端登录时不声明出口能力，服务端不会给它下发出口策略，不影响其既有组网与服务共享。
- 经 Go 或 .NET 服务端的 Peer Mesh 数据面需要升级服务端才能连通（见「Peer 组网修复」）。
- 服务连通性检查需要设备运行本版客户端，旧客户端只能得到「无法判定」。分块续传需要两端都是新页面；与升级前打开的旧页面互传时，128 MiB 以内走旧流程，更大的文件被取消并提示对方刷新。
- 默认关闭：出口分流（租户开关与消费端 `peerEgressEnabled`）、DNS 接管、产品指标。
- 行为变化：没有服务端记录的 HTTP route 不再按公开处理，一律 404，只保留 C 服务端的 `SPECUS_HTTP_ROUTES`；删除仍拥有客户端或接入凭证的管理账号返回 409，需先删除或转移，目前没有转移接口（#237）；非默认租户中新建的管理账号必须在登录框填写租户 ID，升级前已有的账号不填租户仍可登录。
- 数据库结构在启动时自动迁移。Go、.NET、C 服务端上，同一租户内若有两个管理账号的登录名在去首尾空白、转小写后相同，迁移拒绝启动，需先处理。升级前签发的管理 token 在过期前仍然有效，续期后带上 `uid`。
- 出口消费端需要创建虚拟网卡（`peerMeshDevice` 不能是默认的 `noop`），并以管理员或 root 运行（Linux 也可用 `CAP_NET_ADMIN`）。Java 客户端用 `java -jar` 启动时无需改动；自己拼 classpath 或用服务包装器启动的，需要加 `--add-exports java.base/sun.nio.ch=ALL-UNNAMED`，否则 Windows 与 macOS 上作为出口时所有连接都会被拒绝。
- 使用 `deploy/openresty/specus.conf` 的反向代理需要加入新的 `location ^~ /http-share/`，否则临时 HTTP 分享会落到前端页面上。
- Go 服务端的 `SPECUS_NETTY_MAX_FRAME_SIZE` 不能小于 1048587，否则启动失败；默认值 32 MiB 不受影响（#239）。
- C 服务端：Redis URI 按 Lettuce 的规则解析，带下划线的主机名加端口、密码中未转义的 `@`/`#`/`?` 现在会导致启动失败（#341）；客户端配置的 `connectionRateLimitPerMinute` 开始在控制登录时生效（#348）。
- 多实例部署滚动升级期间，旧实例不处理新增的管理身份撤销事件，其上已打开的管理 WebSocket 要到断开时才结束。
- 从源码构建 Go 客户端与服务端需要 Go 1.27.3 或更新的已修补版本，`go.mod` 强制这一下限。
