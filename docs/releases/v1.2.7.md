## 出口分流（一期）

- 新增 Peer 出口分流：消费端按规则把指定 IPv4 地址或网段的流量经已授权的对端设备访问，应用无需逐个配置代理；未命中规则的流量照常从本机出去。命中出口规则但出口不可用时阻断，不回退到本机直连。
- 规则写在客户端配置的 `peerEgressRules` 里，三端共用；动作分 `egress`、`direct`、`block`，前缀更长者优先。出口由服务端租户级开关与每台设备的出口策略共同控制，目标白名单默认全部拒绝，并与基础 Peer ACL 取交集；回环、链路本地与云元数据、组播广播、组网网段与本部署的控制端点永远拒绝。
- Java、Go、.NET 客户端都能作为消费端与出口。消费端在 Linux、Windows、macOS 上接管路由：Linux 用 `ip route`，Windows 经 PowerShell 写入不跨重启的 ActiveStore，macOS 用 `route`。只装精确前缀，已被别人占用的前缀拒绝安装并报告占用者，不抢占；安装记录落盘，正常退出撤回，崩溃后下次启动收回。
- 路由随运行期状态保持正确：虚拟网卡就绪后才应用，之后每 5 秒按当前的对端、中继与控制连接重算，只在计划变化时改动路由表；被别人占用的前缀每 60 秒重试一次。旁路只为被规则覆盖的地址安装，服务端与 STUN/TURN 的主机名在消费端解析后逐个地址旁路。
- 每 5 秒对照真实路由表：切网或休眠恢复后消失的路由、仍指着旧网关的旁路自动补回；前缀被别的路由占走时报冲突、不抢占，对方撤了再装回。
- 出口在 Windows 与 macOS 上连接目标前，把 socket 绑定到隧道之外、系统本来会选的接口（`IP_UNICAST_IF` / `IP_BOUND_IF`），按目标逐个选择，本机同时作为消费端时转发流量也不会绕回隧道；除隧道外没有路由通往目标时拒绝建流，不退回不绑定。
- 规则路由已经覆盖某个地址之后，再为它装旁路（控制端点、STUN/TURN、对端）时，下一跳不再解析回隧道：系统查询回答隧道时改读路由表、去掉隧道后再选。此前这种情况会报 `already resolves to the tunnel`，旁路装不上。
- 新增 `specus-client egress --config PATH [--json]` 与本地管理页「出口分流」面板：逐条列出没生效的规则、没装上的路由、离线的出口设备，其余只计数。`config validate` 在连接前提示不会生效的规则，只打序号与错误码。
- 服务端（Java、Go、.NET、C）提供 `/api/admin/peer-mesh/egress/` 下的开关、策略与活动管理接口，策略变更立即推送给在线设备。管理后台暂无对应页面。
- 使用与排查见 [出口分流使用说明](../peer-mesh/peer-egress-usage.md)，线协议见 [peer-egress.md](../../protocol/spec/peer-egress.md)。

## 一期不支持

- 只支持 IPv4 地址与 CIDR 规则，**域名规则二期提供**；写域名会被拒绝，不会在启动时解析成 IP。
- **不支持 IPv6 规则**，IPv6 目标随二期提供。
- **不转发 ICMP**：命中出口规则的目标 ping 不通，消费端丢弃而不是让它从本机出去。
- **不支持多跳出口链**，也不接管默认路由（`0.0.0.0/0` 规则被拒绝）。
- 目标通常看到出口所在网络的公网出口地址，**不承诺等于出口设备自身地址**。
- **不修改任何持久的系统配置**：不改 DNS、不写持久路由、不改防火墙或内核转发参数。运行期间只向内存路由表添加规则需要的条目，退出时撤回，重启后不存在。

## 这一版修复的问题

- **出口此前在真实部署中无法启用。** 四个服务端只给登录时声明出口能力的客户端下发出口策略，而三端客户端都没有声明（Java 声明了但版本为 0）。现在三端都声明版本 1。
- **Java 客户端此前不加载 `peerEgressRules`**，会提示未知字段并忽略全部规则。现在正常读取。
- **Go 客户端此前对 `peerEgressRules` 误报「未知字段，已忽略」**，实际规则是生效的。现在不再误报。
- **三端此前只在启动时应用一次规则。** Java 在构造组网客户端时应用，此时虚拟网卡还没创建、也没有任何对端会话，控制端点与对端端点的旁路保护没有生效；Go 与 .NET 在启动后应用一次，之后对端连上、中继分配、控制连接重建都不会补装旁路，STUN/TURN 与服务端的主机名从未被旁路。Go 与 .NET 在规则删空时不读安装记录，崩溃留下的路由收不回。现在三端都在网卡就绪后应用、每 5 秒重算，启动时先收回上次的记录。

## 升级说明

- 服务端与客户端都需要升级。旧客户端不声明出口能力，服务端不会给它下发出口策略，不影响其既有组网与服务共享。
- 出口分流默认关闭：租户开关默认关闭，客户端不配 `peerEgressRules` 就不会接管任何路由。
- 消费端需要创建虚拟网卡（`peerMeshDevice` 不能是默认的 `noop`），并以管理员或 root 运行（Linux 也可用 `CAP_NET_ADMIN`）。
- Java 客户端用 `java -jar` 启动时无需改动。自己拼 classpath 或用服务包装器启动的，需要加 `--add-exports java.base/sun.nio.ch=ALL-UNNAMED`，否则 Windows 与 macOS 上作为出口时所有连接都会被拒绝。
- 沿用全端发布流程；发布不代表已部署到运行中的服务器。

## 验证与已知限制

- 规则、授权、帧、控制消息、三个平台的路由读写与出口 socket 的接口选择由共享测试向量钉住，期望值来自独立的 Python 参考实现；三端单元测试与 CLI 真实进程矩阵（Windows / Ubuntu × 三端）覆盖规则告警、登录能力声明、状态查询与本地管理页。macOS 的路由安装、查表与撤销在 CI 的 macOS 真机上执行。
- **跨平台真机验收（#50）尚未完成。** Windows 的路由安装与撤销没有在真机上执行过；macOS 真机验证指向的是回环接口而不是 utun。
- **出口到消费端方向没有发送侧流控**：出口从目标读到多少就立即发出，不看消费端窗口，没有拥塞窗口，靠超时重传恢复丢包。慢链路或丢包链路上下行吞吐会明显退化，**目前没有实测数据**。
- 客户端不处理服务端下发的出口目录、不上报出口计数，因此管理接口的出口活动页总是空的；遇到版本过旧的对端没有专门提示，只表现为出口离线；出口侧没有字节速率限制。
- 路由表被改后最多 5 秒内补回，这 5 秒内命中规则的目标会从本机直连出去；Linux 只对照主表，策略路由导走的流量发现不了。
- 桌面图形界面暂无出口分流页面。#42 本身不关闭：DNS 与域名分流、IPv6 相关条目随二期交付。
