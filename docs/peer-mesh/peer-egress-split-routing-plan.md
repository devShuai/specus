# Peer 出口分流：实现方案与计划

关联 [#42](https://github.com/devShuai/specus/issues/42)。本文只确定方案与分期，不代表任何一项已实现。

## 零、一期交付范围

**一期只做 IP / CIDR 规则。** 域名规则、DNS 接管、fake-IP 全部推到二期——设计已完成，见第八节，但不在一期实现。

这个收窄带来三个后果，先认清再开工：

1. **一期不修改任何用户系统配置。** DNS 是原方案里唯一要动系统设置的地方；去掉之后只剩本功能自己安装的路由，退出即净，也不再需要事务日志与断网风险的兜底设计。
2. **一期不满足 issue 的若干条目**，清单见第七节末尾。它不是「差不多完成」，而是明确的部分交付。
3. **用户写域名规则时必须拒绝**，不能忽略，更不能启动时解析成静态 IP——issue 第 3 节第一条明令禁止这种做法。「先只处理 IP」的意思是域名**明确不支持**，不是用最土的办法凑合。

## 一、现状盘点

### 已经有的，能直接用

| 能力 | 位置 | 对本功能的价值 |
| --- | --- | --- |
| SPM2 加密帧、方向 key、replay 窗口 | 四端 `PeerDataFrameCodec` 及等价物 | 出口数据面直接复用，不新建加密层 |
| 帧内明文多路复用（IPv4 包 / `STMSG2` 应用消息） | `PeerAppMessageCodec` | 出口控制帧可作为第三种明文类型接入 |
| direct/relay 路径选择、TURN 授权 | `PeerMeshClient` | 出口流量天然继承直连与中继回退 |
| SPMTU2 路径 MTU 探测、MSS clamp、ICMP frag-needed 回注 | `PeerPathMtu` / `PeerIpPacket` | 出口路径的 MTU 处理已有现成实现 |
| Linux TUN / Windows Wintun / macOS utun | `*PeerVirtualDevice` | 系统接管的载体已存在，缺的是路由策略而非设备 |
| 服务共享的 TCP/UDP 桥与资源上限 | `PeerServiceBridge` / `PeerServiceUdpBridge` / `PeerServiceResourceLimiter` | 出口侧的连接代理与配额可沿用同一套骨架和常量口径 |
| 服务端 ACL、session、`peer-config` 热下发 | 四端 `PeerMeshService` | 出口授权可复用同一条信令与热生效通道 |
| 本地管理页 v1 契约 | `docs/architecture/cli-local-ui.md` | 规则编辑与状态展示的落点已就绪 |

### 一期要填的缺口

1. **路由只到虚拟 IP**。三端都只装在线 peer 的 `/32` host route，没有机制让指定网段的流量进入 TUN。
2. **数据面只认虚拟 IP**。SPM2 明文校验要求「源=对端虚拟 IP、目标=本机虚拟 IP」，出口流量的目标是任意地址，现有校验直接拒绝。
3. **没有出口侧连接栈**。服务共享是「对端连我，我转本机」；出口是「对端连我，我连任意目标」，方向与授权模型都不同。
4. **没有规则引擎**，也没有跨语言的规则语义定义。
5. **没有出口授权模型**。`PeerMeshAcl` 只表达「两台设备能否互联」，无法表达「允许 A 经 B 访问哪些目标」。

（DNS 面与 IPv6 数据面的缺口留给二期。）

## 二、一期架构决策

### 决策 1：线上传原始 IP 包，出口侧跑用户态连接栈

三个候选：

| 方案 | 消费端 | 出口端 | 结论 |
| --- | --- | --- | --- |
| A. 消费端终结 TCP（tun2socks） | 需要完整用户态 TCP 栈 | 普通 socket | **否**。SPM2 是不可靠 UDP，消费端一旦终结 TCP，就必须在 peer 链路上再实现一套可靠有序流（等于自制 QUIC），两个难点叠加 |
| B. 原始 IP 包 + 出口内核 NAT | 只转发 | iptables / WinNAT / pf | **否**。Windows 侧代价与可靠性都差；按目标授权要把 ACL 翻译成防火墙规则；撤销授权要操作 conntrack |
| C. 原始 IP 包 + 出口用户态连接栈 | 只转发 | 用户态栈终结后用普通 socket | **采用** |

选 C 的理由：

- 消费端数据面几乎不动。丢包和乱序在 peer 链路上发生，就是普通网络丢包，由**应用自己的 TCP 端到端重传**兜住——因为 TCP 的另一端在出口的用户态栈上，不在消费端。
- 出口端不需要任何路由/NAT/防火墙权限，只需要能建普通 socket。这一条直接决定了 Windows 出口是否可行。
- 授权在建流一处判定：收到 SYN 时目标 IP、端口、协议全部已知，查一次 ACL，通过则 `connect()`，不通过则回 RST。撤销授权 = 关 socket，不需要碰内核状态。

代价说清楚：**Java、Go、.NET 各要一个用户态 TCP 终结栈**。这是整个 issue 里最大的单项，收窄到只做 IP 之后它仍然是最大的单项，一点没变小。一期需要的子集：

- 三次握手、四次挥手、半关闭、RST 生成
- 序号/确认、接收窗口、超时重传（Karn + Jacobson RTO）
- MSS clamp（复用现有 `clampTcpMss`）、keepalive、idle timeout
- 拥塞控制一期用保守固定窗口 + 基于已有 RTT/PMTU 观测限速，**明确写为已知限制**，不假装是完整 CC

UDP/QUIC 侧简单得多：源端口映射表 + idle TTL + 每流配额，直接照搬 `PeerServiceUdpBridge` 的骨架。QUIC 作为 UDP 转发是透明的，不需要单独处理。

ICMP 一期不支持（代 ping 需要 raw socket 权限，与「出口零特权」的前提冲突），按 issue 要求明确拒绝并提示，不静默放行。

### 决策 2：只装规则需要的路由，不碰默认路由

不抢默认路由，不装 `0.0.0.0/1 + 128.0.0.0/1` 半程路由。一期只有一类路由：**每条 IP/CIDR 出口规则对应的精确路由 → TUN**。

于是「默认未匹配流量本地直连」不是靠一层兜底逻辑实现的，而是**路由表本身的结果**：没装路由的目标根本不会进 TUN。同时天然满足「不覆盖用户已有路由/VPN 配置」。

反向的防回环 bypass：控制连接、STUN/TURN、peer UDP 端点、出口 peer 自身的地址，全部维护 `/32` 直连路由；出口端的出站 socket 绑定物理接口（Linux `SO_MARK` + 策略路由，Windows `IP_UNICAST_IF`，macOS `IP_BOUND_IF`），确保不回流进自己的 TUN。

路由安装具备事务性：逐条记录本功能写入的路由，失败即回滚已装部分；正常退出、异常终止、重启后都只撤销自己拥有的条目，不触碰其他来源的路由。

用户配置的 CIDR 与既有路由重叠时（例如同时在跑其他分流工具），启动时检测并提示。一期不抢占、不比较 metric，冲突则拒绝安装该条规则并说明，其余规则照常生效。

### 决策 3：出口授权是独立实体，不复用 Peer ACL

新增服务端实体 `peer_egress_policy`，与 `peer_mesh_acl` 正交：

| 字段 | 说明 |
| --- | --- |
| `egressClientId` | 出口设备，稳定标识而非名称/IP |
| `enabled` | 出口设备总开关，默认 `false` |
| `allowedConsumerClientIds` | 允许使用该出口的设备 |
| `destinationRules[]` | 允许的 IP/CIDR + 协议 + 端口区间，**默认空 = 全拒绝**（域名条目二期启用） |
| `scope` | `PUBLIC` / `LAN` 分开授权，互不隐含 |
| `limits` | 并发流数、速率、空闲超时、每消费端配额 |

强制拒绝清单（不受任何宽泛公网规则影响）：回环、链路本地、`169.254.169.254` 及各云元数据端点、组播/广播、mesh CIDR 自身、本部署的控制/STUN/TURN 端点，以及**任何本机 TUN/虚拟接口网段**。

最后一项是防回环规则的延伸：消费端发来的是地址，若该地址落在出口自己的虚拟接口网段内，转发就会绕回出口自身的接管路径。二期引入 fake-IP 后，出口本机的 fake-IP 池段同样加入此清单。

同理堵掉出口串联：`SPEG1` 建流请求携带 hop 标记，出口收到已带标记的请求直接拒绝。**本方案不支持多跳出口链**，一跳即止。

`allowed = 基础 Peer ACL ∩ 出口策略`。基础组网授权**不自动**等于出口授权——服务端下发时就取交集，出口端在实际 `connect()` 前**再校验一次**。目录不可见与数据面不可达必须同时成立，与服务共享的既有口径一致。

### 决策 4：出口流量用新的帧内明文类型

不放宽现有 SPM2 校验（issue 明确禁止绕过独立出口授权）。新增第三种明文，magic `SPEG1`：

| 类型 | 校验规则 |
| --- | --- |
| 裸 IPv4 包（现状） | 源 = 对端虚拟 IP，目标 = 本机虚拟 IP |
| `STMSG2` 应用消息（现状） | 不变 |
| `SPEG1` 出口帧（新增） | 源 = 对端虚拟 IP；目标**必须不在** mesh CIDR 内；必须通过出口 ACL |

`SPEG1` 承载建流请求、建流结果、数据分段与关闭原因。一期建流请求的目标只有地址一种形式，但**协议字段必须同时预留域名形式**——二期加域名时若要改帧格式，四端兼容成本远高于现在留一个字段。

## 三、规则语义

一期只有三类规则：IPv4 单地址、IPv6 单地址、CIDR。动作三种：指定出口、本地直连、阻断。

必须先定死再实现，否则三端一定会长出隐式差异：

- **优先级**：前缀更长者优先；前缀相同时按用户排序，先匹配者胜
- **默认动作**：未匹配 = 本地直连（由决策 2 的路由结构天然保证）
- **规则变更对已建流的影响**：已建流不受影响，除非规则从 allow 变为 deny 或不再匹配，此时立即断开
- **域名条目**：配置校验阶段拒绝，返回明确错误。不忽略、不解析、不降级

二期加入域名与后缀规则时，需要补充「同一目标同时被域名规则和 IP 规则命中」的裁决语义。一期不存在这个问题，但规则模型要为它留位置。

## 四、协议与数据模型增量

新增 `PEER_CONTROL` 消息：

| 类型 | 方向 | 用途 |
| --- | --- | --- |
| `egress-config` | 服务端 → 出口设备 | 下发本机出口开关、目标白名单、消费端白名单、配额 |
| `egress-catalog` | 服务端 → 消费设备 | 下发可用出口列表与其能力（协议、scope、是否支持域名目标） |
| `egress-report` | 出口设备 → 服务端 | 上报活动流数、拒绝计数、故障；用于管理端展示 |

新增管理接口，沿用 `/api/admin/peer-mesh/` 前缀：`GET`/`PUT` 出口开关、`GET`/`POST`/`DELETE` 出口策略、`GET` 出口活动流。

能力协商：`environment.clientEgressCapabilities` 声明 `egressVersion`。版本 `0` 或缺省 = 不支持，服务端不得向其下发 `egress-config` / `egress-catalog`。消费端遇到不支持出口的对端或旧服务端时，明确提示能力不支持，**不降级、不静默直连**。升级默认关闭，不改变现有组网与服务共享行为。

能力字段要能表达「支持出口但不支持域名目标」，这样二期上线时新旧客户端可以共存，而不是靠版本号一刀切。

新增测试向量（沿用 `protocol/test-vectors/` 既有做法）：

- `peer-egress-rules-v1.json`：规则匹配语义，覆盖前缀长度优先级、同前缀排序、默认动作、域名条目被拒
- `peer-egress-frame-v1.json`：`SPEG1` 编解码与拒绝用例，含预留域名字段的前向兼容用例
- `peer-egress-authz-v1.json`：授权判定，含强制拒绝清单与 hop 标记拒绝

## 五、IPv6

一期**纯 IPv4**。IPv6 单地址与 CIDR 规则在配置校验阶段拒绝，不静默忽略、不放行到本地——这是防泄漏要求，不是可选项。

成本拆开看，将来补的时候心里有数：

- **出口侧支持 IPv6 目标很便宜**，只是 socket 地址族不同；用户态 TCP 栈的状态机与 IP 版本正交
- **消费端 IPv6 数据面才是成本**：TUN 要解析 IPv6 头、处理 ICMPv6、PMTU 从 frag-needed 换成 Packet Too Big，现有 `PeerIpPacket` 全部是 IPv4 假设

二期做域名规则时会**顺带获得 IPv6 目标能力**——出口解析到 AAAA 就用 IPv6 socket 连，消费端全程不需要 IPv6 数据面。因此显式 IPv6 CIDR 规则的优先级应排在域名规则之后，那才是真正需要消费端 IPv6 数据面的场景。

为什么 Go 先行：无第三方依赖、TUN 三平台实现最完整、CLI 与本地管理页都在 Go 侧，原型反馈最快。用户态 TCP 栈在 Go 上验证成熟后再移植，比三端并行摸索省得多。

**P3 是关键里程碑**：到此为止就有一个端到端能用的东西了，可以真实跑起来评估用户态栈的实际表现，再决定是否调整后续投入。去掉 DNS 之后这个里程碑提前了整整一期。

## 七、验收策略

- **真机而非 mock**：至少 3 台实机或具备真实 TUN 权限的环境（Windows / Linux / macOS 各一）。CI 里 Linux 可跑，Windows/macOS 的 TUN 建议做成手动触发的 workflow 并归档记录
- **组合裁剪**：3 OS × 3 消费端语言 × 3 出口端语言 = 27 组，全跑不现实。建议 Linux 上跑满 9 种语言组合；Windows/macOS 各跑同语言对角线 3 组 + 一组异构，共 17 组，并在文档里写明裁剪依据
- **防泄漏是独立测试类别**，不是顺带验证。出口离线、ACL 撤销、权限不足、直连/中继切换、客户端崩溃，五个场景各自断言：目标侧**没有**收到来自本机公网 IP 的连接
- **拒绝而非降级**：域名规则、IPv6 规则、不支持出口的对端、旧服务端，四种情况各自断言配置或连接被明确拒绝且有可读原因，不静默忽略、不回退本地
- **安全用例**：未授权设备、跨租户、受限目标、资源耗尽、hop 标记串联，全部由出口侧拒绝并留下脱敏审计
- **性能基线**：吞吐、延迟、CPU/内存、并发上限。**阈值必须在 P7 开始前约定**，不能事后按跑出来的数字反推
- **状态残留**：接管前后、正常退出后、强制终止后、重启后，四个时点比对路由表快照，证明无残留、无越权覆盖
- **日志**：默认不记录请求正文、凭据或完整浏览历史；诊断信息脱敏

### 一期明确不满足的 issue 条目

写下来避免验收时争论：

- 第 2 节「支持精确域名、域名后缀」——不支持域名
- 第 2 节「IPv6 单地址与 CIDR」——不支持 IPv6
- 第 3 节 DNS 与域名分流——整节 5 条全部不交付
- 第 6 节「统一……规则语义」中的域名部分
- 关闭条件中「浏览器和命令行访问命中域名」「DNS、IPv4/IPv6、共享 CDN IP」「DNS 失败」「DNS 重绑定」「DNS 状态残留」等条目

这些随二期交付。#42 在一期结束时**不能关闭**。

## 八、二期：域名分流（设计已完成，不在一期实现）

以下内容已经想清楚，一期不实现，但记在这里避免二期重新推演。

### 域名规则走 fake-IP

命中域名规则的查询**不在本地解析**。从专用池（`198.18.0.0/15`）分配一个假地址，以短 TTL 返回，登记 `fakeIP → 域名 + 规则`。流量到达该假地址时，消费端把**域名**（而非地址）放进出口建流请求，由出口自己解析并连接。

这一个设计同时解掉 issue 第 3 节的大部分条目：

- CNAME、TTL、缓存失效：消费端不缓存解析结果，只缓存 fakeIP 映射，域名到地址的关系完全由出口决定
- 同 IP 多域名 / CDN 共享 IP：每个域名一个独立假地址，不会互相污染
- 多个出口解析差异：各出口在自己网络里解析，本就应当不同
- DNS 重绑定：出口拿到地址后**自己再按 ACL 校验一次**，并且用已校验的地址建连，解析与连接之间不留窗口
- IPv6：出口解析到 AAAA 就用 IPv6 socket 连，消费端全程不需要 IPv6 数据面

边界必须写明：应用自带 DoH/DoT、使用系统缓存、或直接硬编码 IP 时，域名规则**不会**命中，这类流量只能靠 IP/CIDR 规则覆盖。文档、页面和 CLI 帮助都要出现这句话，不能宣称域名规则必然命中。

### 直接访问 IP 的四种情况

| 情况 | 行为 | 是否泄漏 |
| --- | --- | --- |
| 1. 命中显式 IP/CIDR 规则 | 路由已装，包进 TUN，`SPEG1` 建流时目标就是该 IP，出口按 IP 校验 ACL | 否，设计内正常路径（**这就是一期的全部范围**） |
| 2. 只配了域名规则，应用硬编码 IP | 该 IP 没有路由，包不进 TUN，本地直连 | **否**。「未匹配 → 本地直连」是规定行为。但这是**可识别边界**，必须主动告知，不能假装覆盖 |
| 3. 应用长期缓存了 fake-IP，映射仍在 | 正常命中，按登记的域名走出口 | 否 |
| 4. 到达 fake-IP 池内但**没有登记映射**的地址 | **必须阻断** | 放行到出口或回退本地，**这才是真泄漏** |

issue 里的「泄漏」特指命中了出口规则却静默走本地。第 2 种不属于此列，第 4 种是 fake-IP 方案唯一的真泄漏点，必须单独写测试。

### fake-IP 映射的生命周期不等于 DNS TTL

DNS 应答的 TTL 要短，让应用尽快回来问，规则变更才能及时生效；但**映射本身必须活得远比 TTL 长**。应用侧缓存不受我们控制：JVM 曾长期默认永久缓存，浏览器和各类客户端也各有策略。TTL 一到就回收映射，等于把长缓存的应用推进第 4 种情况。

- 映射按 LRU 保留，下限以小时计，不随 TTL 到期回收
- 池容量 `198.18.0.0/15` 约 13 万个地址，正常使用下不会耗尽；接近上限时按 LRU 淘汰并记录，不静默复用
- 淘汰的地址进入隔离期再复用，避免旧连接打到新域名上
- 池段可配置，启动时检测与本机现有路由的冲突，冲突则拒绝启动并提示，不猜测

### DNS 接管方式——二期开工前需要拍板

要让应用的查询到达我们，只有改系统 DNS 一条可靠路径。按目的端口劫持做不到，因为路由是按目的地址决定的。

因此接管期间必须把系统 DNS 指向 TUN 上的本功能地址。与「不覆盖用户配置」的调和方式：

- 启用前记录原值，落盘到事务日志
- 退出、异常终止、重启后均可完整回滚，只撤销本功能写入的状态
- 未命中域名规则的查询原样转发到记录下来的原上游，不改写、不缓存
- 首次启用时明确告知这一改动

**这是整个方案里唯一需要修改用户系统配置的地方**，也正因为如此，一期把它整体推迟了。若二期开工时仍不接受这一改动，域名规则不可实现，功能范围就永久停在 IP/CIDR。

### 与既有 fake-IP 环境的冲突

同类方案（Clash 默认 `198.18.0.1/16`、sing-box 默认 `198.18.0.0/15`）与本方案的默认池段直接重叠，用户同时开启并不罕见。冲突有两层：

- **路由层可解**：两者抢装同一段到各自 TUN，靠池段可配置绕开
- **DNS 层无解**：系统 DNS 只有一个设置，两个方案都要指向自己，后改的赢；挪池段救不了

因此不追求共存。启动时检测到以下任一条件就**拒绝启动并说明原因**，不静默继续——不可预测的分流比不工作更糟：

- fake-IP 池段已被其他接口的路由占用
- 系统 DNS 当前指向回环或某个 TUN 接口地址（强烈暗示已有接管者在场）
- 池段与 mesh CIDR、本机任一接口地址、或已配置的 IP/CIDR 规则重叠

第二条牵出一个回滚陷阱：**记录「原始 DNS 上游」时，若当前值本身就是回环或 TUN 地址，不能把它存为原值**。将来回滚会把用户指向一个已经不存在的接管者，直接断网。这一步必须拒绝启动，而不是老实记录。

物理网络真的在用该段的情况同样存在（RFC 2544 保留段被企业内网违规当私有段使用）。校验规则同上，但**不能只在启动时做**：切网后新网络可能落进池段。网络变更事件要重新校验，冲突则停止接管并告警，不静默继续。

对端处在 fake-IP 网络里则**不需要处理**，这正是「发域名而非地址」的红利：出口在自己的环境里解析和连接，内部怎么走与我们无关。fake-IP 的作用域被限制在单机内，不会顺着 peer 链路传染。

### 不做 DNS 学习路由，不靠 SNI 嗅探兜底

两个看起来能救第 2 种情况的做法，都不采用：

- **把出口解析出的真实 IP 反向加进路由**：CDN 场景下一个 IP 被多域名共用，会误伤无关流量；出口的解析结果在消费端未必可达；还会让路由表随 DNS 抖动。
- **TLS SNI 嗅探**：只对已经进了 TUN 的流量有效，救不了压根没进 TUN 的第 2 种情况；ECH 普及后 SNI 本就会不可见。

第 2 种情况的正解是让用户补规则，不是我们猜。可执行的策略：规则测试器输入 IP 时显式说明「该地址未被任何规则覆盖，将本地直连」；对需要完整覆盖的服务，文档给出「域名规则 + 该服务已知 IP 段的 CIDR 规则」的组合写法；可选的 DoH/DoT 阻断开关默认关闭，且必须写明它是启发式、不完备。

## 九、风险

| 风险 | 应对 |
