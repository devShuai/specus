## 2. 结论摘要

当前互传页面已经具备较完整的产品能力：

- 文件选择、拖放和粘贴发送；
- WebRTC Direct、TURN 和登录用户 OSS 兜底；
- 剪贴板文本、富文本、链接和文件同步；
- 同步白板、房间角色、邀请链接和配对码；
- 文件接收进度、预览、保存和分享；
- 深浅色模式、键盘页签操作和移动端响应式布局。

当前主要问题不在功能数量，而在任务编排和操作安全感。页面仍然更像一个功能集合面板，没有把用户最关心的流程稳定地组织成：

1. 确认房间和连接状态；
2. 明确选择接收设备；
3. 选择要发送的内容；
4. 查看逐项进度和传输结果；
5. 必要时重试、取消或保存。

本次审计确认 2 项 P0、5 项 P1、3 项 P2。优先处理以下风险：

- 切换网络或房间会无确认地中止传输并清空本地内容；
- 当前目标离线后可能自动改选另一台设备，与“粘贴即发送”组合后存在误发风险；
- 服务异常、正在连接和确实没有设备被混合为相近状态；
- 手机端在发送区之后才展示目标设备，前置条件与操作顺序相反；
- 多文件传输缺少逐文件任务、取消、重试和结果历史。

## 5. 问题明细

### UX-01：切换网络或房间无确认地清空当前上下文（P0）

#### 当前行为

`PublicTransferPage.tsx:1071` 的 `updateNetworkMode()` 在切换内网/外网时直接执行：

- `resetTransferRoomState()`；
- `clearIncomingItems()`；
- 中止当前文件任务；
- 清空设备列表和当前目标；
- 清空剪贴板、白板和流程图事件；
- 释放接收文件的本地预览 URL。

房间设置应用、新建房间和加入新房间也存在相近重置行为。`SyncedClipboard.tsx:164` 和 `SyncedWhiteboard.tsx:450` 会在 scope key 变化后清空本地剪贴板块和白板。

#### 用户影响

- 传输过程中误触网络开关会立即中止任务；
- 尚未保存的直连文件可能从页面消失；
- 未导出的白板内容和剪贴板历史会被清空；
- 页面只在切换后提示“已切换”，没有在操作前说明代价；
- 手机端网络开关触控面积较小，误触成本更高。

#### 建议方案

- 传输进行中时禁用网络、房间和 Token 切换；
- 检测未保存文件、剪贴板块或白板内容；
- 有内容时弹出统一的离开当前房间确认框；
- 提供“保存后切换”“直接切换”“取消”三个明确选择；
- 切换前自动保留可恢复的本地草稿；
- 新房间作为独立操作，不与普通设置保存处于同一层级。

#### 验收标准

- 传输进行中不能通过一次点击切换网络或房间；
- 存在未保存内容时必须确认；
- 取消确认后所有内容和连接保持不变；
- 切换后的提示明确说明哪些内容被保留、哪些内容已停止；
- 恢复旧房间时可以找回本地草稿。

### UX-02：目标设备可能静默切换（P0）

#### 当前行为

`PublicTransferPage.tsx:789` 在设备列表更新时：

- 当前目标仍在线则保持；
- 当前目标离线或未选择时，自动选择 `visiblePeers[0]`。

同时：

- 文件在选择后立即发送；
- `SyncedClipboard.tsx:339` 在存在目标时执行“粘贴即发送”；
- 页面没有要求用户在目标被自动替换后再次确认。

#### 用户影响

- 原目标离线后，新加入的第一台设备可能自动成为目标；
- 用户继续粘贴或选择文件时，内容可能发送给非预期设备；
- 目标选择位于右侧栏或手机页面下方，不容易发现已经变化；
- 对剪贴板、图片和私密文件构成明显隐私风险。

#### 建议方案

- 目标离线后立即回到“未选择设备”，禁止自动改投；
- 第一台设备出现时可以推荐，但不应直接成为可发送目标；
- 文件区、剪贴板输入区和白板协作区持续显示“发送给/正在与谁同步”；
- 目标变化时显示显著但不打断的状态提示；
- 粘贴即发送前必须存在用户明确选择且仍在线的目标；
- 可以记住同一房间内的明确选择，但不能跨房间复用。

#### 验收标准

- 目标离线后不会自动选择其它设备；
- 未明确选择目标时，粘贴只保存在本地，不发送；
- 每个发送入口都能在首屏看到目标名称；
- 设备重名、离线和重新上线时不会造成目标身份混淆；
- 自动化测试覆盖“目标 A 离线、目标 B 在线后继续粘贴”的场景。

### UX-03：连接状态与错误反馈不完整（P1）

#### 当前行为

`PublicTransferPage.tsx:846` 在获取 WebSocket ticket 失败时直接把异常消息写入全局 `error`。`PublicTransferPage.tsx:2654` 用大面积红色错误框展示该文本。

实际页面出现了以下组合：

- `Internal Server Error`；
- “0 台设备”；
- “还没有发现内网设备”。

当前没有独立的发现连接状态，服务不可用和确实没有其它设备都主要表现为 `peers.length === 0`。连接恢复后的 `hello` 和 `onopen` 也没有明确清除旧错误。

#### 用户影响

- 用户无法判断是网络问题、服务器问题还是对方尚未加入；
- 英文底层错误削弱产品完整感；
- 红色错误框覆盖整个主流程，但没有重试操作；
- 即使自动重连成功，旧错误仍可能让用户认为页面不可用。

#### 建议方案

建立独立状态机：

- `connecting`：正在连接房间；
- `connected-empty`：已连接，等待其它设备；
- `connected`：已连接且存在设备；
- `reconnecting`：连接中断，正在重试；
- `offline`：多次重试失败；
- `name-conflict`：设备名称冲突；
- `permission-denied`：房间权限失效。

主界面只显示用户可理解的说明，例如“连接暂时中断，正在重试”。底层 HTTP 状态和异常文本放进“查看详情”。错误区域增加“立即重试”和“检查房间设置”操作。

#### 验收标准

- 服务不可用时不再显示“没有发现设备”；
- 错误信息全部本地化；
- 自动重连成功后旧错误自动消失；
- 每种失败状态至少提供一个可执行的恢复操作；
- 错误反馈通过 `role="alert"` 或合适的 `aria-live` 被辅助技术感知。

### UX-04：手机端发送前置条件顺序错误（P1）

#### 当前行为

文件选择区位于 `PublicTransferPage.tsx:2602`，目标设备区域位于 `PublicTransferPage.tsx:2780`。桌面端目标设备在右侧栏，手机端变为单列后，目标区域排在：

- 房间控制；
- 功能页签；
- 当前功能内容；
- 收到的文件；

之后。

文件选择按钮仍然可以点击，只在内部文案提示“请先从设备列表选择一台内网设备”。

#### 用户影响

- 用户先看到可操作的文件框，却无法完成发送；
- 提示要求选择设备，但设备列表位于页面更下方；
- 多设备情况下，用户需要在输入区与设备区之间反复滚动；
- 剪贴板“粘贴即发送”与目标设备之间缺少足够强的视觉关联。

#### 建议方案

- 将目标设备选择器放到房间栏和功能页签之间；
- 桌面端可保留右侧详细设备栏，但主区仍显示当前目标；
- 手机端使用单行目标选择器或底部设备选择 Sheet；
- 未连接设备时将文件框主操作改成“邀请设备加入”；
- 未选择目标但存在设备时，主操作改成“选择接收设备”；
- 选择目标后再切换为“选择文件并发送”。

#### 验收标准

- 390px 视口首屏能够看到房间状态、目标设备和当前主操作；
- 用户不需要向下滚动即可完成目标选择；
- 目标为空时不会打开文件选择器后才报错；
- 手机端目标选择器触控高度不低于 44px；
- 多设备切换后，文件区和剪贴板区同步更新目标名称。

### UX-05：房间设置过密且主次动作混乱（P1）

#### 当前行为

`PublicTransferPage.tsx:2432` 的内联设置区域同时包含：

- 新房间、恢复、应用；
- 客户端名称和单独的保存；
- 房间名称；
- 房间 Token 和生成；
- 邀请权限；
- 接收前确认；
- 权限邀请记录和撤销操作。

内网模式仍显示禁用的 Token、生成按钮和权限选项。手机端同时出现多个蓝色或近似主按钮，实测部分开关、单选项和页签高度为 24 至 36px。

#### 用户影响

- “保存”和“应用”的作用范围不清楚；
- 内网用户看到大量不可用设置；
- 新房间与普通保存并列，容易误触；
- 设置展开后把当前传输内容推到首屏之外；
- 过多同级强调色造成视觉焦点分散。

#### 建议方案

- 桌面端改为右侧设置抽屉，手机端改为底部 Sheet；
- 设置分为“设备”“房间”“接收与隐私”“邀请权限”四组；
- 只展示当前模式可用的字段；
- 统一一次保存，客户端名称可在失焦时单独校验；
- “新建房间”放入更多菜单，并在有内容时确认；
- 主页面只保留房间名称、连接状态、目标设备和邀请入口。

#### 验收标准

- 主页面设置收起时不承担表单布局；
- 内网模式不出现禁用的 Token 和权限表单；
- 同一个面板最多只有一个主按钮；
- 所有手机触控目标不低于 44 x 44px，紧凑图标按钮也具有足够命中区域；
- 保存成功后明确指出实际修改的内容。

### UX-06：缺少逐文件传输任务模型（P1）

#### 当前行为

页面在 `PublicTransferPage.tsx:265` 附近只维护：

- 一个全局传输 `state`；
- 一个全局 `progressStore`；
- 一个完成 `record`。

`PublicTransferPage.tsx:1604` 对多文件进行顺序循环，后一个完成记录会覆盖前一个。当前进度组件仅描述当前全局状态。

#### 用户影响

- 无法知道批量文件中具体哪一个成功或失败；
- 无法单独取消、重试或移除某个文件；
- 看不到速度、剩余时间和等待队列；
- 页面刷新或切换后缺少可理解的结果历史；
- “已处理 N 个文件”不能说明是否全部成功。

#### 建议方案

引入统一传输任务模型，每个任务至少包含：

- 文件名称、类型和大小；
- 目标设备；
- 当前路径的用户化名称；
- 排队、连接、发送、接收、完成、失败、取消状态；
- 已传字节、百分比、速度和预计剩余时间；
- 取消、重试、保存、打开、清除操作；
- 失败原因和恢复建议。

主区显示最近任务，完整历史放入可展开活动中心。批量文件按队列逐项展示，不再只显示一个总进度。

#### 验收标准

- 批量发送时每个文件都有独立状态；
- 单文件失败不会覆盖其它文件结果；
- 进行中任务可以取消；
- 失败任务可以直接重试；
- 发送方和接收方都能看到文件名称、目标/来源和进度；
- 所有任务完成后显示成功数、失败数和可重试数量。

### UX-07：跨页签文件活动不可见（P1）

#### 当前行为

工具页签会计算文件和剪贴板活动数量，但 `index.css:3137` 将 `.app-apple-tool-tab-detail` 永久隐藏。白板激活时，收到的文件区域也被隐藏。

#### 用户影响

- 在白板中收到文件时可能没有明显提示；
- 需要手动确认的文件可能长时间无人处理；
- 失败、完成或等待保存的状态缺少跨功能可见性；
- 用户无法判断哪个页签有新内容。

#### 建议方案

- 页签显示未读数量、进行中状态和失败标记；
- 收到文件、完成和失败使用非阻塞通知；
- 移动端提供固定的活动入口；
- 正在传输时，即使切到白板也保留简洁进度条；
- 待确认文件使用更高优先级提醒，但不遮挡白板操作。

#### 验收标准

- 任意页签下都能看到进行中的文件数量；
- 新文件到达后文件页签出现未读徽标；
- 点击页签并查看对应任务后清除未读；
- 失败状态不会只存在于已隐藏的面板；
- 通知不会重复弹出或覆盖关键控制。

### UX-08：技术术语和中英文混用（P2）

#### 当前行为

主界面直接展示：

- `nearby`；
- `Direct/TURN`；
- `OSS`；
- `Paste · Drop · Click`；
- `direct`；
- 服务端英文异常。

#### 用户影响

- 用户需要理解网络协议才能判断当前状态；
- 中英文混用削弱界面一致性；
- “仅 Direct/TURN”没有回答用户真正关心的“是否可用、失败后怎么办”；
- 技术路径被赋予过高视觉权重。

#### 建议方案

采用用户任务语言：

| 当前文案 | 建议文案 |
|---|---|
| `nearby` | 附近设备 |
| 内网 / 外网 | 附近 / 远程 |
| 仅 Direct/TURN | 点对点传输 |
| OSS 兜底可用 | 云端接力可用 |
| Paste · Drop · Click | 粘贴、拖放或选择文件 |
| direct | 点对点 |
| TURN | 中继 |

协议名称、候选路径和 HTTP 错误保留在“传输详情”或 FAQ 中。

#### 验收标准

- 主操作流程不要求用户理解 WebRTC、TURN 或 OSS；
- 所有可见状态文案使用统一语言；
- 技术详情仍可被高级用户查看；
- 同一个状态在发送方、接收方和 FAQ 中使用相同名称。

### UX-09：工具页首屏信息层级偏宣传化（P2）

#### 当前行为

`PublicTransferPage.tsx:2384` 使用较大的标题和介绍段落。默认功能页签却在 `PublicTransferPage.tsx:274` 固定为剪贴板，页面名称和用户历史心智仍以“互传文件”为主。右侧还长期保留 8 项 FAQ。

#### 用户影响

- 工具页首屏空间被重复介绍占用；
- 默认剪贴板与“文件互传”的主要进入意图不一致；
- FAQ 在手机端显著增加页面长度；
- 首屏缺少唯一、明确的主任务。

#### 建议方案

- 标题缩成一行工具标题；
- 首屏直接显示房间、目标和当前任务；
- 默认打开文件传输，或记住用户上次使用的页签；
- 邀请链接可以携带建议打开的功能；
- FAQ 收入帮助弹窗或工具菜单；
- 空状态承担引导职责，不再重复介绍性段落。

#### 验收标准

- 桌面和手机首屏都能看到实际主操作；
- 返回页面时恢复上次使用的功能页签；
- 从文件邀请进入时直接定位文件任务；
- FAQ 不再占用主流程固定空间；
- 页面只有一个明确的主操作。

### UX-10：手机白板和触控无障碍不足（P2）

#### 当前行为

`SyncedWhiteboard.tsx:222` 将白板最小宽度固定为 720px，手机只能看到局部。`SyncedWhiteboard.tsx:310` 默认工具为画笔，触摸后会进入绘制而不是平移。部分页签、单选和开关的实际高度为 24 至 36px。

全局错误和成功提示没有统一的语义化 live region。

#### 用户影响

- 手机首次进入白板时缺少整体方位感；
- 用户需要先理解“移动”工具才能浏览画布；
- 横向滚动、绘制和页面滚动之间容易冲突；
- 小触控目标容易误触；
- 屏幕阅读器不能及时获取连接和传输结果。

#### 建议方案

- 手机首次进入时自动“适应宽度”；
- 支持双指缩放和平移；
- 触摸设备默认移动工具，首次绘制后可记住选择；
- 提供缩放比例、适应内容和回到原点；
- 所有主要触控目标使用至少 44px 命中区域；
- 对连接、错误、完成和待确认状态使用正确的 `aria-live`；
- 对非文本图标保持稳定的可访问名称和选中状态。

#### 验收标准

- 390px 手机首次打开能够看到完整白板宽度；
- 双指缩放不会触发绘制；
- 单指行为与当前工具一致且可预期；
- 工具按钮命中区域不低于 44px；
- 键盘可完成页签切换、设备选择、发送、取消和重试；
- 屏幕阅读器能够读出连接、进度和完成状态。

## 8. 建议验收清单

### 操作安全

- [x] 网络切换不会无确认地丢失内容；

- [x] 只读用户无法进入可发送状态。

### 连接与反馈

## 9. 建议度量指标

上线改造后建议持续观察：

- 从打开页面到成功发送第一个文件的中位时长；
- “打开文件选择器后因未选择设备失败”的比例；
- 目标设备变更后的取消率和误发反馈；
- 房间或网络切换导致的任务中断率；
- Direct、TURN、OSS 各路径成功率，但仅在诊断界面展示协议；
- 多文件任务的失败、重试和取消比例；
- 手机端邀请完成率和首个目标选择耗时；
- 待确认文件的响应时间；
- 错误恢复后继续完成发送的比例。

## 10. 当前实现值得保留的部分

- 文件支持选择、拖放和粘贴，输入方式完整；
- 页签具备 ARIA 语义和方向键切换；
- 文件接收已经具备进度、预览、保存和分享基础能力；
- 剪贴板支持文本、富文本、链接和文件分流；
- 白板工具已经进行菜单归并，并支持导入导出；
- 深浅色模式总体风格统一；
- `prefers-reduced-motion` 已被考虑；
- 房间角色和接收前确认已经具备产品基础。

后续改造应保留这些能力，重点调整它们出现的顺序、状态反馈和操作约束，而不是重新堆叠新的卡片或说明文字。
