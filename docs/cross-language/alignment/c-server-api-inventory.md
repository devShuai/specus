## 读法

- **一致**：C 有对应实现，行为与 Java 一致，并有测试依据（下列 C 测试、中央向量，或 `c-server-test-map.md` 中记为「覆盖」的 Java 测试类）。
- **有差异**：C 有对应实现，但有已知的行为差异，“说明”写出差异；平台差异另在第 8 节列明原因。
- **没有**：C 没有对应实现。
- **未逐项对照**：C 有对应路由，鉴权与主要形状已核对，但请求校验、状态码等细节没有逐项对照 Java，也没有对照测试；列为待办（第 9 节），不算作一致。
- **本分支**：本分支修正过的行，提交见第 10 节。
- Spring 在进入 controller 之前拒绝的请求回 400，分两种（以 Java 服务端实测为准，见第 9 节第 9 项）。**请求体**缺失、不是对象或成员类型不符（`HttpMessageNotReadableException`）与**必填参数缺失**，Spring Boot 的错误体以 `"error":"Bad Request"` 表示状态，C 回同样的 400 与 `{"error":"Bad Request"}`，不带 `timestamp`、`path` 等字段；在任何处理与鉴权之前被 Tomcat 或 Spring Security 的 `StrictHttpFirewall` 拒绝的请求同样（Java 的正文分别是 Tomcat 的 HTML 错误页与 Spring Boot 的错误体，第 9 节第 10 项列出规则），只有 `TRACE` 是 405、`CONNECT` 是 501。**路径变量与查询参数转换失败**（`MethodArgumentTypeMismatchException`）则由 Java 的 `GlobalExceptionHandler` 按其原因回 `{"error":"<原因的消息>"}`：数字是 `NumberFormatException` 的 `For input string: "<去掉空白后的值>"`（十六进制另带 ` under radix 16`，`0x-5` 是 `Sign character in wrong position`），布尔是 `Invalid boolean value [<原值>]`。转换规则：包装类型（`Long`、`Integer`、`Boolean`）的空白值等于没给，基本类型（`long`、`int`、`boolean`，路径变量都是）的空白值转换失败、空串取默认值；数字去掉全部 Java 空白，`-` 之后的 `0x`/`0X`/`#` 按 `Long.decode` 读十六进制，其余按 `Long.valueOf`，任何文字的十进制数字都算（`Character.digit`）；布尔先 `trim`，认 true/false/on/off/yes/no/1/0（不分大小写）；参数按 Java 方法里声明的顺序转换，第一个失败的作答。同名参数给了多次时，`String` 得到逗号连起来的全部值；数字与布尔先由 ConversionService 只转第一个值（空串是 `null`，基本类型不收；空白值转不了），失败再交给属性编辑器转逗号连起来的全部值，于是消息里是全部值（`clientId=a&clientId=1` 答 `For input string: "a,1"`，`page=&page=` 答 `","`）。参数名也按百分号解码，没有 `=` 的参数是空串。请求体按 Jackson 绑定：Peer Mesh、映射新增、客户端新增与修改、HTTP 路由新增与修改、凭据的 `enabled`、客户端下载链接与管理用户（缺请求体或不是对象 400；数字字符串可转 `Long`/`Integer`，带小数的数截断，`"TRUE"`、`"True"`、整数可转 `Boolean`，`"1"`、`"yes"`、`"tRUE"` 不行，对象或数组不能转 `String`；枚举只认常量名（去掉首尾空白）或序号）。`fix/c-server-parity-crud`、`fix/c-server-parity-peer-api` 建立了这套绑定，当时把转换失败也答成 `{"error":"Bad Request"}`，由 `fix/c-server-path-variable-binding` 按实测改正。
- 鉴权：「公开」= `SecurityConfig` 中 `permitAll`；「Bearer」= 需要管理端本地 HS256 token（C 每次请求按 SQLite 重新读取用户）；「Bearer（任意）」= `/api/public/transfer/attachments/**`，任何已认证主体；「ticket」= WebSocket 一次性 ticket。

本分支修正的偏差（第 10 节有提交）：Elasticsearch 搜索、可见范围、写入队列、节点列表与 `tcp-streams` 契约；TCP 帧采集顺序；超过 32 KiB 的管理读应答被静默丢弃；客户端、映射、路由、凭据、用户、客户端目录列表的固定行数上限（超过后 500 或静默截断，目录截断后客户端看不到最新版本）；概览字段；管理员看不到已删除客户端和未知名称的连接记录；流量统计 `limit` 上限；客户端到管理员消息不检查来源账号；写入失败回执；命令 JSON 映射严格性；`/ws/connections` 的二进制与未掩码帧。

`fix/c-server-parity-crud` 修正的偏差（第 9 节第 5、7 项，提交见第 10 节末）：凭据与映射的找不到、apiKey 重复原先回 404/409，Java 是 400 并带 id；凭据的 `maxOnlineInstances` 不限范围、生成的 apiKey 与 secret 形状不同、更新应答不带 `"secret":null`；映射更新的字段原先可省略、省略 `enabled` 时保留原值、公网端口只在同一客户端内查重；映射列表与两个流量统计的 `clientId` ≤ 0 不过滤，非数字参数被忽略；名称可用性的 `excludeClientId` 不可见时 404；`/me` 的时间戳为空串；初始化把演示客户端写进固定的 `default` 租户；管理员看不到已删除客户端的流量统计，资源类型不规范化；注册先校验字段再做人机验证、文案与 Java 不同、长度按字节计；Peer 服务导入按整个租户去重；这几类视图的时间戳是 SQLite 的 `YYYY-MM-DD HH:MM:SS`。

`fix/c-server-parity-peer-api` 修正的偏差（第 9 节第 8 项，提交见第 10 节末）：Peer Mesh / Egress 27 个端点的请求绑定、检查顺序、文案、状态码（新增回 200、删除回 200 无正文、找不到回 Java 的 400 或 404）、视图字段（设备只列已有的、`null` 而非占位值、会话的 `lastKeepaliveAt`、开关的 `null`）与 ISO-8601 时间；管理端关闭会话、关闭设备、改 ACL 后通知两端（`close`）；服务目标与导入候选按 `requireTargetHost`；映射新增不再是同客户端同端口的 upsert，公网端口全局唯一，客户端找不到 400；客户端、路由、下载链接、连接记录、月度统计、用户、流程图、ACL、设备、会话、服务、出口策略与开关、共享与审计视图的时间由 SQLite 的 `YYYY-MM-DD HH:MM:SS` 改为 ISO-8601；其余带类型的查询参数按 Spring 转换；`X-Forwarded-Host` 取第一个；构建带 libbrotlidec 时解码 `br`。

`fix/c-server-parity-edges` 修正的偏差（第 9 节第 2、3、6 项，提交见第 10 节末）：Peer Mesh 列表与全库客户端列表的固定行数上限、会话列表缺 Java 的分页形式；SQLite 流量搜索的字段、通配与 WHERE 长度，管理员看不到已删除客户端的流量；普通用户看到按名称匹配的失败登录；`listenPort=0`、`clientId` ≤ 0 不过滤；裁剪时 `total_data_set_size_in_bytes` 为 0 改读 `size_in_bytes`；`/ws/connections` 文本上限与 UTF-8 校验；命令成员为数字或布尔值时读作缺失。

| 流控：帧写进浏览器 socket 之后才回 `WINDOW_UPDATE`，浏览器停读时客户端的 credit 停在 1 MiB 窗口处，服务端为它排着的不超过这个窗口 | 一致 | 同 Java（写完才回）。积压排空的过程中，已写出帧的 credit 攒到 256 KiB（窗口的四分之一）或队列空了才一起回，不再每帧一个 `WINDOW_UPDATE`；字节数不差，只是 Java 每帧回一次。浏览器侧已在关闭时丢弃的帧照常回 credit，同 Java `processWsData` 不论写成败都回。`direct_websocket_backpressure_tests`：客户端用满窗口后 1.5 s 内再收不到 credit，发出的远少于 64 MiB 的上限 |
| CLOSE 的先后：客户端的 SWS2 CLOSE、无 CLOSE 的 FIN（1001）、客户端违规（1002，随后断开）排在已入队的帧之后；回应浏览器的 CLOSE、浏览器侧协议错误（1002/1007/1009）、隧道断开与客户端 RST（1011）、data 连接断开（1001）、分享结束（1008）排在积压之前，未发出的帧丢弃；排在积压之前且代码不是 1000 时，正在写的帧与 CLOSE 合计只有 50 ms | 一致 | Java 每帧写完才处理下一帧，客户端的 CLOSE、FIN 与违规必在它之前的帧写完之后；Tomcat 自己产生的 CLOSE 不排在其他发送者之后，非 1000 用 50 ms（`ABNORMAL_SESSION_CLOSE_SEND_TIMEOUT`）。客户端 RST 与 data 连接断开时 C 丢弃还没写出的帧；Java 没有队列，这些帧在它处理 RST 之前已同步写完（写的期间整条 data 连接停着），只在浏览器跟不上时可见，RST 按 `control-protocol.md` 本就是立即取消。`direct_websocket_tests`「a stalled browser's CLOSE goes ahead of the queue」：排着 1 MiB 时浏览器发 CLOSE，之后只收到少于 16 帧就收到回应的 CLOSE，丢弃帧的 credit 回给客户端；「a stalled browser's stream ends at once」：浏览器停读时客户端 RST 与 control 断开都立即返回，浏览器连接随即断开。服务端自己产生的帧（PONG、回应、拒绝）写失败只断开浏览器连接，不算浏览器写失败：浏览器发 CLOSE 后立即复位连接时，它的 CLOSE 照样转给客户端，流仍以 FIN 结束（同原先同步写时忽略这一失败）；只有承载客户端数据的帧写失败才让流以 `RST 31` 结束。`direct_websocket_tests`「a failed answer to the browser's CLOSE keeps the stream's FIN」 |
| 浏览器的 PING：PONG 紧跟正在写的帧，不排在积压之后；已排队但还没写的 CLOSE 之前照常回 PONG（CLOSE 仍是最后一帧，RFC 6455 5.5.2）；尚未发出的 PONG 被新的替换（5.5.3 只要求回应最近的 PING） | 一致 | Tomcat 由读线程直接发 PONG，Java 排在客户端 CLOSE 前面的帧还在同步写时也照常回应。`direct_websocket_tests`「a stalled browser's PING is answered ahead of the queue」「a stalled browser's PING is answered ahead of a queued CLOSE」 |
| 分享结束（到期、撤销、路由停用等）关闭分享 WebSocket 时不等浏览器 | 有差异 | 原先维护线程（到期）或撤销请求要拿该流的写锁并同步写 1008，遇到停读的浏览器会无限期卡住；维护线程卡住时全部分享的到期切断、peer-mesh 目录过期与注册清理都停摆。现在只把 1008 入队，客户端随即收到 RST（`HTTP share ended`），浏览器在 50 ms 预算后断开。Java `terminate` 先发 RST，再在 `synchronized(session)` 内关闭会话，会等正在阻塞的 `writeFrame`（最多 20 s）；C 不等，比 Java 好。`http_share_tests`「revoking a share whose WebSocket browser reads nothing does not wait on it」：撤销 2 s 内答 200，客户端的流以 RST 结束，浏览器连接断开 |
| 客户端越过窗口：等浏览器写出的客户端帧超过 4 MiB 时该流 `RST 6`（`stream send queue exceeded`），浏览器以 1011 关闭 | 有差异 | C 独有（第 8 节）；守 1 MiB 窗口的客户端碰不到。`direct_websocket_tests`「a client overrunning its window gets RST 6」 |
| 浏览器发往客户端：客户端不回 credit 时暂停读浏览器（TCP 背压），不断开 | 有差异 | G8 已核实：Java `handleAppFrame` 用 `sendAtomic` 入 `StreamFlowController` 队列而不暂停 Tomcat 读取，1 MiB 窗口用完后再排满 4 MiB 即 `RST 6`（`stream send queue exceeded`）并以 1011 关闭浏览器；C 与 Go、.NET 一样等 credit 并暂停读取，符合 `control-protocol.md`「credit 不足时暂停对应上游读取」（第 8 节）。`direct_websocket_tests`「close credit timeout」用满窗口后不再转发 |
| 浏览器发来的单条消息上限 16 MiB（超出 1009） | 有差异 | G9 已核实：`WebSocketSpecusHandler` 继承 `AbstractWebSocketHandler`（不收分片消息），也没有调用 `setTextMessageSizeLimit`/`setBinaryMessageSizeLimit`，Tomcat 默认消息缓冲 8192（文本按字符、二进制按字节），超出即以 1009 关闭，客户端收到 SWS2 CLOSE 1009 + FIN；`PublicTransferDiscoveryWebSocketHandler` 的注释与 `ClientMessagesWebSocketHandler` 调高上限都印证这一默认值。C 与 Go、.NET 一样按 `http-route.md` 第 7 节的 16 MiB（第 8 节）。`direct_websocket_tests`「browser violations」：恰好 16 MiB 的分片消息照常转发，多 1 字节即 1009 |

## 8. 平台差异（不实现）

| 差异 | 原因 |
| --- | --- |
| 管理事件协调不等于数据库 HA | #261 已实现 kind 4 连接事件与 kind 5 身份撤销的 Redis 扇出、租户绑定和本地授权过滤；#35 第 45 项起 Redis 断开后与 Lettuce 一样自动重连并重新订阅（`management_cluster_e2e.py`），断开期间的事件与 Java 一样漏收。C 仍只用 SQLite，这不提供分布式管理数据库、跨节点数据复制或 HA 接管 |
| Redis URI 只接受 `redis://[user[:password]@]host[:port][/0..15]`（先 trim）；`rediss://`（TLS）、`redis-sentinel://`、unix socket 与查询参数都拒绝启动 | C 用 hiredis 的同步连接，没有接入 TLS 传输和 Sentinel 的主节点发现；Java 的 Lettuce 都支持，Sentinel 还能在主从切换后跟到新主节点。C 部署须把 Redis 放在私有可信网络、指向固定的主节点地址；该地址后面的 Redis 重启或切换由自动重连恢复。db 编号上限 15 只在 Redis 配置了超过 16 个库时才与 Java 不同 |
| 集群事件队列除 4096 条外另有 64 MiB 载荷上限 | Java 的事件执行器只按条数限制。C 常跑在小内存设备上，4096 条 256 KiB 的事件就是 1 GiB；超出任一上限都与 Java 一样丢弃新事件并记日志，订阅不受影响 |
| 未配数据库时，未消费的公开互传 ticket 每来源最多 1024 张（IPv6 按 /64 计为一个来源，超出时拒绝该来源 `429`），总量最多 16384 张（超出时淘汰最旧的一张，不拒绝任何人）；配了数据库时与 Java 一样不限 | Java 总把 ticket 存库。C 未配数据库时把 ticket 放在进程内存，匿名签发需要内存上界；按来源计数让单个来源签满也挡不住别人，总量处淘汰最旧的而不是拒绝，免得 16 个来源（或一个 IPv6 /64 内的大量地址）把所有人挡在外面。正常浏览器 45 秒内只会持有一两张，且一般一秒内就消费 |
| 集群配置的空值：`SPECUS_PUBLIC_TRANSFER_CLUSTER_ENABLED`、`…_PRESENCE_LEASE_SECONDS`、`…_PRESENCE_REFRESH_INTERVAL_MS`、`…_REDIS_COMMAND_TIMEOUT_MS` 设为空串（`NAME=`）时 C 用默认值 | Spring 把 `${NAME:default}` 解析成空串（默认值只在变量不存在时才用），转换器对空串返回 null，绑定到 primitive 字段失败，Java 不能启动；刷新周期的空串另外让 `@Scheduled` 缺少调度参数而失败。环境文件里 `NAME=` 通常表示“用默认值”，C 保留这一常见写法，不因此拒绝启动。只含空白的值与 Java 一样拒绝启动；其余取值（布尔词表、数字的去空白与十六进制、刷新周期须为正的十进制数且与集群开关无关）都与 Java 相同 |
| `SPECUS_NETTY_MAX_FRAME_SIZE` 大于 32 MiB 时按 32 MiB 读（启动时记一行），登录请求不论 `SPECUS_NETTY_PRE_AUTH_MAX_FRAME_SIZE` 多大都以 16 KiB 为限；`specus.netty.*` 设为空串（`NAME=`）时用默认值 | C 的协议层按 32 MiB 分配和校验帧体，登录请求另有 16 KiB 的命令级上限（`protocol.c`）。Java 与各语言客户端发出的帧都远小于这两个值，调小（限制每连接内存）与 Java 完全一致，调大才看得出差别。空串的处理与上一行集群配置相同：Spring 绑定到 primitive 失败、Java 不能启动，C 保留 `NAME=` 表示用默认值的常见写法；只含空白与其余绑定不了的值同 Java 拒绝启动（#35 第 45 项 NAT-BP-08） |
| 每条公网 TCP 连接占一个读线程和一个写线程；`SPECUS_NETTY_MAX_EXTERNAL_CONNECTIONS*` 默认按 Java 的 10000 | Netty channel 不占线程，C 的转发用阻塞读写。按 Java 的默认值，一个端口满 10000 条连接时就是 20000 个线程（每个线程 8 MiB 栈的地址空间、两个映射），描述符上限（常见默认 1024）通常先到，accept 失败时监听按 Netty 暂停 1 s 而不再关闭端口。小内存设备可以用这三个变量（或旧名 `SPECUS_MAX_*_EXTERNAL_CONNECTIONS`）调低；已结束的连接立即回收线程与内存（NAT-BP-01、07） |
| 发现 socket 的单帧写超时默认 5 秒（Tomcat 阻塞发送为 20 秒） | 两边超时后都关闭该连接；C 的默认值更短，让停读的浏览器更早被关闭，`SPECUS_PUBLIC_TRANSFER_DISCOVERY_WRITE_TIMEOUT_SECONDS` 可调到 300 秒 |
| Redis 命令在每条连接上串行（状态命令一条、PUBLISH 一条、订阅一条） | hiredis 同步上下文不能并发，Lettuce 在一条连接上多路复用。C 已按 Java 用 MGET 读 presence、findPeer 只读、roster 事件按 (group, net) 只读一次快照、续期每个 net 每周期只发布一次，PUBLISH 也像 Java 的 `eventPublishConnection` 走单独连接，每条消息的往返次数与 Java 相同，只是不能并行 |
| SQLite 明细同步写入，没有待写队列；`inspection-status` 在 SQLite 下 pending/dropped 恒为 0 | 本地写库不阻塞网络；Java 的队列为保护转发线程，C 只对 Elasticsearch（网络写入）使用 |
| Elasticsearch 待写队列另有 256 MiB 总量上限 | C 服务常跑在小内存设备上；Java 只按条数（每类 20000）限制 |
| 关停时写出全部待写文档，Java 只写一批 | 只会少丢数据 |
| Elasticsearch 节点按顺序故障转移，不轮询 | libcurl 单连接；轮询只影响负载分布，不影响结果 |
| 没有 libbrotlidec 的构建不解码 `br`（brotli）：HTTP 明细的预览与详情按解不开处理（显示原字节），媒体清单按存储的原字节处理 | `fix/c-server-parity-peer-api` 已按方案接入：`CMakeLists.txt` 用 `pkg_check_modules(BROTLIDEC libbrotlidec)`、`Makefile` 用 `pkg-config` 可选检测，找到时定义 `ST_HAVE_BROTLI` 并链接；`decompression_limits.c` 以 `BrotliDecoderDecompressStream` 按 `decompression_limits` 的同一上限流式解码（预览只读前缀，同 Java `readLimited`），`traffic_capture.c`（预览与详情）与 `media_capture.c`（清单）在 gzip/deflate 旁加 `br`。CI（`protocol-v2.yml` 的 C server 任务）与发布（`release.yml`）的 apt 依赖已加 `libbrotli-dev`，这些构建与 Java 一致；只有自行构建且没装 `libbrotli-dev` 的环境（如本机 WSL）走「未检测到」分支，保持原状。libbrotlienc 也在时，`decompression_limits_tests` 另测压缩炸弹与往返 |
| `/api/admin/peer-mesh/service-audit` 的审计存在 SQLite，按租户列最近 50 条，重启后仍在 | Java 把审计放在进程内存的一个队列里，全局只留最近 80 条（各租户共用），重启即清空。C 写进 `peer_mesh_service_audit` 表：同样的字段与顺序，多租户时不会被别的租户的事件挤掉，也不随重启丢失；改成内存队列只会丢数据 |
| Peer Mesh 关闭且没有 standalone STUN 时，`stun-config`/`ice-config` 不把 `STUN_ALTERNATE_PUBLIC_ADDRESS` 列进 STUN 服务器 | Java 的 `standaloneAlternateStunServer` 不看 Peer Mesh 开关，这时内置 STUN/TURN 没在监听，列出的是一个没有服务的端点；C 只在发布自托管 STUN 时列出备用地址（`fix/c-server-parity-peer` 起的取舍，test-map `PublicPeerMeshResourceTests` 行） |
| `database/initialize` 的 `orm`/`dialect` 为 `sqlite3`/`sqlite` | 报的是实际实现：C 直接用 sqlite3 API，没有 JPA 与 Hibernate 方言 |
| 不建 Java 的演示凭据 `demo-client`（secret `test1234`） | 公开的固定凭据，C 从不写入（test-map `LegacyDemoCredentialSanitizerIntegrationTests` 行）；演示客户端照常建 |
| 流量计数写库失败时整批加回，下次全部重写 | Java `flush()` 在一个事务里逐个写计数器，出错时只把出错的那一个加回再抛出，同一事务里已写的其他计数器随回滚丢失；C 也在一个事务里写整批，失败时整批加回。只在数据库出错时可见，C 只会少丢数据（issue #35 第 45 项） |
| 管理 WebSocket 每个连接一个写线程、待写积压有上限（每个连接 4096 帧或 16 MiB；所有连接尚未发出的帧合计 64 MiB，帧在各连接间共享、只算一次；超出时有积压的连接以 1001 `Send queue full` 关闭），一个慢连接不耽误别的连接 | Java 用 Tomcat 阻塞发送，发送线程本身就是背压，不需要队列，代价是同一次广播里排在后面的 session、登录线程与集群事件线程都要等它（每个停读的 session 每个 8 KiB 块最多 20 s）。C 不让任何共享线程等某个浏览器，就必须按连接排队，队列必须有界：每个连接的上限挡住单个慢连接，合计上限挡住许多慢连接一起占内存（例如任一已登录用户开很多个窗口极小、不读的 `/ws/client-messages`，再让自己的客户端发大消息；共享帧之后同一条消息无论排给几个连接都只占一份）。正常浏览器（包括网速慢的）的积压远小于上限；停读的浏览器通常先碰到与 Java 相同的 20 s 写超时，只有事件密集到 20 s 内积压超过上限时才先碰到上限。两种情况的结果相同：该连接被关闭，连接保持期间从不丢帧；队列为空的连接总能收下一帧，所以跟得上的连接不会因为别人积压而被关；管理端 `useConnectionsFeed` 会带退避重连 |
| 路由 WebSocket 每条一个写线程，data 连接的读线程只把客户端帧入队；一个停读的浏览器只拖住它自己，同一 data 连接上的其他流一点不停 | Java 在 data 连接的 Netty event loop 上用 Tomcat 阻塞发送写浏览器，一个停读的浏览器让同一客户端的全部 TCP、HTTP、WebSocket 流（含心跳应答）停住，直到 20 s 发送超时；分享结束时 `terminate` 也在 `synchronized(session)` 上等这次写。C 只有一个读线程读 data 连接，若照搬阻塞写，停读的浏览器每次都会冻结该客户端 20 s，任何公网访客都能反复这样做；所以 C 让写线程去等，发送超时、超时后关闭该 WebSocket 与流控（写出才回 credit）仍与 Java 相同 |
| 路由 WebSocket 等浏览器写出的客户端帧超过 4 MiB 时该流 `RST 6`（`stream send queue exceeded`），浏览器以 1011 关闭 | 写线程需要有界队列。credit 只在写出后回，守 1 MiB 窗口的客户端最多排 1 MiB，永远碰不到；不守窗口的客户端按 TCP 流队列满的处理（Java `StreamFlowController` 同为 4 MiB 与 `RST 6`）。Java 写浏览器不排队，不守窗口的客户端只会让 event loop 阻塞得更久 |
| 路由 WebSocket 的待写队列只有每流 4 MiB 的上限，没有管理 WebSocket 那样的合计上限 | 与 TCP 流的 4 MiB 队列相同。守窗口的客户端每条流最多排 1 MiB（写出才回 credit），合计随并发流数增长，而每条流本来就占着一个浏览器连接、一个读线程和一个写线程；Java 不排队，但同样为每条流持有它的会话与在途消息。合计上限只能靠关闭守规矩的流来执行，管理 WebSocket 那样的 64 MiB 会让许多正常的慢浏览器被误关，所以不设 |
| 路由 WebSocket 写浏览器超时后，客户端立即收到 `RST 31` | Java 此时的 `afterConnectionClosed(1006)` 要发 code 1006 的 SWS2 CLOSE，被自己的 `WebSocketSpecusFrame` 拒绝（规范禁止 1006 上线），异常被 Spring 吞掉：客户端只照常收到该帧的 `WINDOW_UPDATE`，收不到 CLOSE、FIN 或 RST，直到它再在该流上发 DATA/FIN 才得 `RST 7`，分享 WebSocket 的在途名额也不释放。浏览器不带 CLOSE 断开（1006）时 Java 同样如此。这是 Java 的缺陷，C 不照搬：上游因此会挂着一个永远没有浏览器的 WebSocket |
| 路由 WebSocket 浏览器灌入速度超过客户端时，C 暂停读浏览器，不断开 | Java `handleAppFrame` 用 `sendAtomic` 入队而无法暂停 Tomcat 的读，1 MiB 窗口加 4 MiB 队列满后 `RST 6` 并以 1011 关闭浏览器。`control-protocol.md` 要求 credit 不足时暂停对应上游读取，Go 与 .NET 也暂停；规范站在 C 一边，应改的是 Java |
| 路由 WebSocket 浏览器发来的单条消息上限 16 MiB（超出 1009） | Java `WebSocketSpecusHandler` 没有调高 Tomcat 默认的 8192 消息缓冲（文本按字符、二进制按字节），浏览器超过 8 KiB 的消息即以 1009 关闭。`http-route.md` 第 7 节与 `control-protocol.md` 都写 16 MiB，Go 与 .NET 也是 16 MiB；改成 8 KiB 会让依赖大消息的应用在 C 上失败，应改的是 Java（在 `afterConnectionEstablished` 里把两个上限设为 16 MiB） |
| 公网监听每个连接占一个线程，同时处理的请求只受 `maxConnections`（8192）约束；没有 Tomcat 那种 200 个工作线程、多出的请求排队的限制 | Tomcat 的 NIO 连接器只在处理请求时占用工作线程，空闲连接和已升级的 WebSocket 都不占。C 的连接在整个生命周期里都占着一个线程，WebSocket 也一样。如果把线程限制在 200，第 201 条 WebSocket 或 SSE 长连接就会让管理接口完全停摆。所以 C 只照 Tomcat 的 `maxConnections`/`acceptCount` 限制连接数（`SERVER_TOMCAT_MAX_CONNECTIONS`、`SERVER_TOMCAT_ACCEPT_COUNT`），卡住的连接靠 60 s 读写超时释放（#35 第 45 项）。可观测的差别是：同时有超过 200 个路由请求在等设备时，Java 让后来的请求（连同管理接口）排队，C 照常处理；单条 data 连接另有 1024 个 pending 的上限，见下面一行 |
| `/http/**` 与 `/http-share/**` 的请求体先整体读进内存（最多 `SPECUS_HTTP_MAX_REQUEST_BODY_SIZE`，默认 16 MiB），读完才向设备发 OPEN | Java `HttpSpecusController` 先发 OPEN，再按 64 KiB 边读边发，每块都要等到窗口。C 的转发器接口拿的是完整请求体；改成流式，要连带重写 chunked 解析、上限与 trailer 收集、明细采集和分享路径，本项没有改。可观测的差别：设备在上传结束前看不到请求，upstream 无法提前答复（例如 401、413）。客户端离线或路由未配置时，也要先收完请求体才答 502/404。chunked 请求体超限时设备完全看不到请求；Java 下设备会先收到 OPEN 和 16 MiB 数据，再收到 `RST 8`。上传中途停住超过连接超时时，C 答 `400 HTTP 请求体不完整`，设备看不到请求；Java 答 502，并对设备发 `RST 8`。内存方面，每个并发上传最多占一份请求体上限，总量由连接数上限与读超时兜住，但仍远高于 Java 每个请求约 64 KiB 的占用 |
| 响应体超过 64 MiB 时发 `RST 4`，浏览器拿到截断的响应 | 与 Go server 相同；http-route.md 第 4 节的「响应体上限 64 MiB」是对整条链路的要求。Java server 自己不设这个上限，靠 Java、Go、.NET 客户端各自的 64 MiB 限制。只有不自限的客户端才看得到差别（[运行时语义](runtime-semantics.md) 已记录） |
| 每条 data 连接最多 1024 个 pending Direct HTTP 流，第 1025 个请求答 `502 HTTP 流创建失败` | Java `NatServerHandler` 的流表不设上限，并发只受 Tomcat 200 个工作线程限制，超出的请求排队。C 的每个 pending 流占一个连接线程和一份接收队列，所以按 data 连接设上限；答复文案沿用 Java 打不开流时的那句。停读的访客会在连接超时后释放名额，不会把名额永久占满。SSE、长轮询这类长期挂着的请求超过 1024 个时，C 直接拒绝新请求，Java 则让后续请求（连同管理接口）排队 |
| 单个响应 DATA 帧超过 64 KiB 时只复位该流（`RST 8`） | control-protocol.md 规定 NAT DATA 分片上限为 64 KiB。Java `HttpStreamExchange` 只按 1 MiB 窗口与 4096 个事件检查，单帧可以大到 Netty 的帧上限；Go 也不按单帧检查。C 按规范校验，只有违反规范的客户端看得到差别，同一 data 连接上的其他流不受影响 |
| 临时分享在响应头之前被切断时，C 直接中断访客连接，不作答 | temporary-http-share.md 6.6 要求「HTTP 直接中断响应」，Go 也是中断。Java 在响应尚未提交时答 `502 HTTP 转发请求失败`，只有已提交才中断。设备一侧两者相同，都收到 `RST 8 HTTP share ended`；明细也按 Java 记 `502 HTTP share ended`（#35 第 45 项） |
| `/ws/client-messages` 发往客户端的在途写按 socket 64 条、全局 1024 条限制，超出立即回 `failed`/`target-write-failed` | Java `channel.writeAndFlush` 不看 `isWritable`，消息在 Netty 出站缓冲里无界排队，写完回 `written`，通道关闭时回 `failed`。C 每条在途写占一个线程并阻塞在目标 control 连接上（受 `SPECUS_CONTROL_WRITE_TIMEOUT_SECONDS` 约束），线程与内存都必须有界。只有目标 control 连接停读、发送缓冲已满时才会出现 64 条在途；此时 Java 的排队也只是推迟结果（目标恢复读则 `written`，断开则 `failed`），C 对超出的部分立即答 `failed`。`management_ws_backpressure_tests` 场景 3 固定这一行为 |
| 每个 TURN allocation 同时有效的 permission 与 channel 各 32 个，一个 CreatePermission 最多 32 个对端，超出回 `400 bad-request` | Java/Go 用 Map 保存、不设上限。C 给单个已认证客户端能占用的内存设上界；过期的条目每秒清理并让出位置，浏览器 ICE 与 Peer Mesh relay 同时用到的对端远少于 32 个（`stun_turn_tests` 的 `test_expired_permissions_and_channels_recycled`；Issue #35 第 45 项） |
| 备用端口上的 TURN 消息与未知方法：只对请求回 `400 unsupported-endpoint` / `400 unsupported-method`，指示与响应静默丢弃 | Java 对能解析的任何 STUN 消息都回 400。对错误响应再回一个错误响应，会在两台服务器之间、或源地址伪造成服务器自己时来回反弹；请求得到的应答与 Java 相同（`test_turn_wire_details`） |
| Allocate 找不到可用的 relay 端口或 socket 时回 `508 insufficient-capacity` | Java `bindRelaySocket` 抛出异常，被接收循环吞掉，客户端收不到应答、只能重传到超时；C 立即回一个明确的错误 |
| 没有中继相关的 Micrometer 指标：`specus.peer_mesh.turn.*`（relay 队列深度、高水位与丢弃，发送失败，通用中继字节、配额拒绝、目的地址拒绝与字节配额关闭）与 `specus.peer_mesh.relay.traffic.*`（flush 失败、待写字节、flush 滞后） | C 没有指标注册表与导出端点（`/api/admin/metrics` 是管理概览，不是 Micrometer），Java 默认的 actuator 也只暴露 health。对应事件 C 写日志：配额拒绝、字节配额关闭与目的地址拒绝写 `[peer-mesh][audit]` 行，批量写库失败写 `[peer-mesh] relay traffic flush failed` 行；relay 发送没有工作队列，见 test-map `StunTurnServerMetricsTests` 行 |
| 会话关闭后，关闭前已经中继、还没写库的那批 relay 字节照记 | Java 本实例关闭会话（`markClosed`）时丢弃这部分 `pendingRelayBytes`，别的实例关闭的会话则照记（`persistRelayTrafficBatch`）；C 一律照记，只会少丢数据 |
| 停止时写出待写的 relay 字节 | Java `PeerMeshService` 没有 `@PreDestroy` 的 flush，停止时最多丢掉一个 flush 间隔（默认 5 秒）的待写字节；C 在 STUN/TURN 停止时写出，只会少丢数据 |
| 内置 STUN/TURN 起不来（端口被占用、公网地址或 `SPECUS_PEER_MESH_RELAY_ADDRESS` 解析不了、严格 RFC 5780 配置不全）时，告警行 `[peer-mesh] standard STUN/TURN UDP server failed to start on <端口>` 不带原因，原因在它之前单独成行（例如 `cannot resolve the advertised STUN/TURN address ...`） | 行为与 Java 相同：记一条告警后服务照常运行，只是没有 STUN/TURN（`peer_mesh_e2e_tests` 的 "the server runs on when STUN/TURN cannot start"；C 原先整个进程退出）。Java 把异常消息接在同一行，C 在出错的地方就写出原因 |

8。评审跟进（同一分支）又改了五处，跟进新增的测试都先在本分支上一版 `b4952f8` 上失败：上传阶段写 data 连接失败原先没有被察觉（发送函数不论成败都释放数据包，失败标志恒为 0），浏览器多半得到「客户端不在线」，现按 data 连接断开答 `HTTP 转发请求失败`、记 `control channel closed`；原先一看到升级头就撤掉两个超时，只带升级头、没有 WebSocket 处理器接手的请求（静态文件、包下载、管理 API、路由请求）因此没有写超时，现在只有处理器接手后才撤掉读超时，写超时为 Tomcat WebSocket 的 20 s，阻塞写也按进展重新计时；媒体分片上传原先每片一个线程，现按 Java 的线程池设置：最多 `uploadThreads` 个工作线程，排队上限 `max(线程数, 线程数 × 在途数 × 4)`（默认 64），超出时由转发线程自己上传（`CallerRunsPolicy`）；`SERVER_TOMCAT_MAX_CONNECTIONS`、`ACCEPT_COUNT` 按 Spring `NumberUtils.parseNumber` 绑定（去掉所有空白，`0x`、`#` 为十六进制）；转发响应时 sink 自身失败（例如内存不足）不再算作客户端中断，尚未发出字节时答 502，并记 `HTTP response could not be relayed`。
