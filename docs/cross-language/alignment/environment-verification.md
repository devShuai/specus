## 当前仍存在的不一致与环境门禁

- Go 标准库不暴露逐 listener backlog，也没有与 Netty event-loop 一一对应的 worker thread 数；对应配置保持 Java 兼容，实际 backlog 使用操作系统 `somaxconn`，连接并发由 goroutine 调度。功能与安全门禁已对齐，但调优旋钮不是同构实现。
- .NET 的内存 TestServer/TestHost 不提供生产 Kestrel 使用的原始 HTTP Upgrade feature；生产路径使用自实现 RFC 6455 transport，控制帧与边界由低层确定性测试覆盖，仍需在部署环境补 Kestrel 端到端 Upgrade 验收。
- Android 已补真实测试 CA/hostname TLS 握手；生产 CA、L4 TLS 终止与多平台证书存储仍需环境验收。
- 真实 MySQL/PostgreSQL、RustFS/OSS/Elasticsearch、跨 NAT direct/relay、真机 VPN/TUN 和长时间压力仍属于发布验收，不作为源码单测通过的替代结论。
- C server 尚未闭合的证据项（已有结果见上节「当前验证」，此处只列缺口）：Java/Go/.NET client × C server 的心跳、TCP、Direct HTTP/WebSocket 与运行时热更新已在 CI 通过（上节 run 37387624598），不再是缺口。尚缺：真实私有 OSS/Elasticsearch、Android client × C server（没有命令行客户端）、任何客户端 × C server 的 Peer Mesh 信令与 TURN relay、OIDC 的 ID Token 校验与本地登录（C 未实现）、客户端启动鉴权 nonce 防重放（C 未实现）、管理 JWT 按数据库当前状态重新解析（C 未实现）、Go/.NET server 与 C 的 Redis 混部、跨 NAT direct/relay、长时间/多客户端压力和真实 TLS/OIDC。Java/C Redis discovery 已通过，但在这些外部门禁完成前仍不能并入 Java/Go/.NET 的完整互换与生产替换结论。
