## 阶段 6：TLS、数据库和端到端验证

状态：源码主路径已完成，外部数据库与真实部署矩阵仍待验收。

- Java 是参考实现。
- Go server 支持控制通道与管理 HTTP TLS，`file` 模式已对齐 Java/.NET 的 PKCS12 / PFX keystore 读取；未配置 keystore 时仍兼容 PEM 证书和私钥文件。
- .NET server 支持 EF Core 多库和 TLS 配置；管理用户、流量明细、总流量租户字段、Peer Mesh、`transfer_attachment`、房间/流程图、HTTP 媒体采集、session 消息能力与 ACL direction 均已补齐 SQLite/MySQL/PostgreSQL provider-specific migration，并保留启动时幂等 SQL 兼容历史库。
- Java、Go、.NET、C server 的启动登录响应统一返回 `nettyTls`（C 自 2026-10-06 起，此前缺失使 TLS 监听的 C server 对未显式启用 TLS 的客户端不可用）；Java、Go、.NET、Android 四种客户端在未显式覆盖时跟随该信号，并统一支持 PEM CA、证书主机名覆盖、系统信任与仅开发使用的跳过校验。管理 HTTPS 不再被误当成 control/data 原始 TCP TLS。
- C server 的源码能力已覆盖 control/data TLS、OIDC code 交换代理（不含 Java 的 ID Token 校验与本地登录，见[安全差异](security-differences.md)）、密码/邮件验证注册、Direct HTTP/WS/SWS2、客户端消息、Redis 多实例 discovery、持久房间/流程图、Aliyun OSS 附件（唯一 provider）、HTTP 媒体采集、可选 Elasticsearch 明细、托管客户端包/GitHub fallback，以及 Peer Mesh roster/session/service signalling 与内置 RFC 5389/5780 STUN、RFC 5766 TURN relay。管理、对象、媒体和 Peer Mesh 路径共享 SQLite tenant/owner/client/session 身份与失败关闭策略；定时维护会清理注册验证码、对象下载授权/过期附件、媒体对象/分片和 Peer Mesh session/catalog/relay lease。TLS 1.2+ 支持 PKCS#12/PEM，prod 拒绝自签和公网明文监听；HTTPS/OIDC/GitHub/对象存储请求默认验证证书链和主机名。这是源码范围，不是运行证据：哪些能力有单测、集成测试或端到端运行，以及 Java server 测试在 C 侧的对应项，见 [C server 测试对照](c-server-test-map.md)。
