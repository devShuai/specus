# Peer Mesh 客户端的职责拆分方案

## 现状

同一个类在四端都长到了同一个量级：

| 实现 | 文件 | 行数 |
| --- | --- | --- |
| .NET | `Specus.Client/PeerMesh/PeerMeshClient.cs` | 5034 |
| Android | `PeerMeshEngine.java` | 5003 |
| Java | `specusclient/peer/PeerMeshClient.java` | 4386 |
| Go | `internal/client/peer_mesh.go` | 4024 |

四端独立写成、却收敛到相近的体量和相同的内部结构，说明这不是某一次疏忽，而是这个类**承担的职责集合本身**决定的。Go 那份有 156 个顶层函数，按名字里的主题词统计：

| 主题 | 函数数 |
| --- | --- |
| UDP 收发与地址处理 | 35 |
| STUN | 20 |
| TURN | 19 |
| candidate 生命周期 | 17 |
| NAT 探测与分类 | 15 |
| 路径选择与切换 | 13 |
| relay | 10 |
| 密钥与帧加解密 | 13 |
| 虚拟网卡与数据包 | 13 |

.NET 那份有 235 个成员方法。这些数字不是要证明"太大"——大小本身不是缺陷——而是要说明它同时是 STUN 客户端、TURN 客户端、NAT 探测器、候选地址状态机、路径选择器、加密帧编解码器和虚拟网卡数据面。改动其中任何一项，都要在一个装着另外六项状态的类里做。

## 拆分为什么值得做

**这七件事的变更节奏完全不同。** STUN/TURN 是 RFC，多年不变；NAT 探测和路径选择是启发式，会随实测数据反复调整；帧格式变更要四端同步；虚拟网卡是平台相关的。它们被同一把锁和同一份状态绑在一起，于是调一个启发式参数要理解 TURN allocation 的生命周期。

**四端必须逐字节一致的部分，和四端可以各写各的部分，现在混在一起。** 帧格式和 STUN/TURN 属于前者，线程模型和缓冲策略属于后者。混在一个类里，评审时无法只看必须一致的那部分。

**这是本次审计里若干缺陷的共同土壤。** Go 客户端把每个直连数据帧都丢掉的那个 bug（SPM2 magic 落在 TURN ChannelData 区间内，分类只看区间不看解析结果），本质是"TURN 解复用"和"数据帧分发"两个职责挨在一起却没有明确边界。Android 那批阻塞问题同样出在数据面和控制面共用一个执行上下文。

## 目标结构

按变更节奏和一致性要求切，而不是按行数平均切。四端使用相同的边界与命名，这样跨语言评审可以逐块对照。

```
PeerMeshClient                 编排：把下面几块接起来，持有生命周期
├── StunClient                 RFC 5389/5780 请求与响应解析
├── TurnClient                 allocation、refresh、permission、ChannelData
├── CandidateSet               候选地址的状态机与生命周期
├── NatProbe                   NAT 类型探测与分类（启发式）
├── PathSelector               直连/中继选择、切换、RTT 平滑（启发式）
├── PeerFrameCodec             X25519/HKDF/AES-GCM、replay window、SPM1/SPM2
└── VirtualDataPlane           虚拟网卡读写、包过滤、路由同步
```

边界的判据是**谁需要知道谁的状态**：

- `StunClient` 和 `TurnClient` 只处理协议，不知道 peer 是谁，也不做选择。它们是四端必须一致的部分。
- `CandidateSet` 持有候选状态，但不决定用哪个。
- `PathSelector` 读候选状态做决策，不自己发包。
- `PeerFrameCodec` 是纯函数加一个 replay window，四端必须一致，可以用共享向量交叉验证。
- `VirtualDataPlane` 是唯一平台相关的部分，已经在 Go 里按 build tag 分开，其余三端应对齐这个形态。
- `PeerMeshClient` 只剩编排：它知道所有人，其他人互相不知道。

## 分阶段

拆分一个跑在生产路径上的 4000 行类，一次性重写的风险高于收益。按"每一步都可独立验证、可独立回滚"来切：

**第一阶段：抽出纯函数部分。** `PeerFrameCodec` 和 `StunClient` 的编解码没有可变状态，抽出来不改变任何行为，且立刻能用现有的跨语言向量验证。这一步风险最低，同时把"必须四端一致"的代码集中到了可以单独评审的位置。

**第二阶段：抽出 `TurnClient`。** 它有状态（allocation 生命周期）但边界清晰。这一步同时修掉 TURN 解复用与数据帧分发的耦合：解复用改为"尝试解析，成功才认领"，而不是"落在这个区间就认领"——正是 Go 那个 bug 的根因。

**第三阶段：抽出 `CandidateSet`，再抽 `NatProbe` 和 `PathSelector`。** 顺序不能反：后两者读候选状态，先把状态收拢到一个所有者，它们才有干净的依赖方向。这一步之后，调整启发式不再需要理解 TURN。

**第四阶段：抽出 `VirtualDataPlane`。** 放在最后是因为它平台相关，四端形态差异最大，且需要真机验证，不适合在前面几步的回归尚未稳定时动。

每一阶段在四端同步进行并各自跑全量测试；不要让某一端先走完四步，否则跨语言对照会在中间状态失效，而这个类的价值恰恰在于四端一致。

## 不做的事

**不追求行数指标。** 目标是让每一块有单一的变更理由，不是让每个文件小于某个数字。`VirtualDataPlane` 拆完可能仍有上千行，那没有关系。

**不引入跨语言共享代码生成。** 四端各自手写、用共享向量交叉验证，是当前的既定取舍；拆分不改变这一点。

**不在拆分的同一个提交里改行为。** 唯一的例外是第二阶段的 TURN 解复用，那是已确认的缺陷，且与边界调整不可分割——它会被单独说明并单独测试。

## 验收

- 每一阶段结束时四端全量测试通过，且跨语言向量测试仍然逐字节一致
- 拆分后 `PeerMeshClient` 只保留编排：不直接构造 STUN/TURN 报文，不直接读写虚拟网卡
- `PeerFrameCodec` 与 `StunClient`/`TurnClient` 可以在不启动网络的情况下单测
- 调整一个 NAT 探测启发式参数，改动不触及 TURN 或帧编解码文件
