# 客户端管理归属转移（v1，#237）

关联 [issue #237](https://github.com/devShuai/specus/issues/237)。读者是 Java、Go、.NET、C 服务端与管理前端的实现者。

**状态：产品边界已确认；接口与一致性规则为实现草案，尚未交付。** 不能据此宣称四端已有这些接口。账号身份、目标查找与租户语义沿用 [management-accounts.md](management-accounts.md)，客户端凭证与身份关系沿用 [client-auth.md](client-auth.md)。

## 1. 已确认的产品边界

本功能叫「转移管理归属」，不叫「设备安全交接」。只允许本租户管理员操作。

- 一份接入凭证可以派生多台设备。共享凭证下的单设备转移必须返回 `409`，不能自动把其他设备一起转走，也不能只改一个客户端而留下凭证归属。
- 提供独立的「整组转移」入口：展示凭证与全部受影响设备的清单后，由管理员显式确认。
- 首期不更换 `apiKey`、secret 或设备密钥，不因转移而一律吊销客户端会话。知道原接入密钥的人仍可登录；尚未过期的客户端访问 token 仍按既有认证条件使用。停用、过期、删除等原有限制不变。
- 管理权限随新归属改变。保留接入能力不等于保留原所有者的后台权限，也不等于保留原先基于「同一所有者」得到的 Peer 访问权。

确认界面必须显示：「仅转移管理归属。原接入密钥与有效客户端会话保留，持有密钥的人仍可接入；这不是安全交接。」完整安全交接另行设计，不包含在本版本中。

## 2. 转移范围

「客户端」指客户端账号，不是管理账号；「设备清单」列出这些客户端账号。关联凭证按 identity 的 `credential_id + client_id` 关系查找，不能按用户名、在线会话或显示名猜测。

| 情况 | 单设备转移 | 整组转移 |
| --- | --- | --- |
| 旧客户端没有关联凭证 | 改客户端与同租户 Peer 设备行的归属 | 无凭证组入口 |
| 凭证只关联一个客户端 | 同事务转移该客户端、Peer 设备行与凭证 | 也可从凭证入口转移 |
| 凭证关联多个客户端 | `409 CREDENTIAL_SHARED`，零改动 | 转移凭证及其关联的全部客户端、Peer 设备行 |
| 凭证尚未关联客户端 | 不适用 | 允许，只转移凭证；以后派生的客户端归新所有者 |

清单包括在线、离线与停用的客户端，按客户端 ID 升序排列并去重；不只统计当前在线会话。凭证与客户端可以有不同的旧所有者，整组转移要逐项展示，并将它们统一转给目标账号。不得顺带转移这些旧所有者的其他凭证或客户端。

关联客户端已不存在、关联跨租户、同一客户端关联多个凭证等不一致数据必须失败关闭，返回 `409 INCONSISTENT_CREDENTIAL_GROUP`，不透露其他租户内容、不先修复或部分转移。清单不能截断：大组可在前端分页展示，但确认绑定完整集合。

目标是调用者租户内存在且已启用的管理账号，以规范登录名查找，保存该账号的实际登录名，不保存账号键或用户输入的大小写变体。默认租户中当前可用于管理登录的内置管理员也可作为目标；其他租户不能选它。不存在、跨租户或停用目标统一 `400 INVALID_TARGET_OWNER`，不枚举其他租户的账号。账号不存在于数据库不妨碍处理遗留的旧归属。

## 3. API 与确认

新增接口不复用普通客户端/凭证编辑请求，以免未展示影响范围的编辑操作静默转移。

| 接口 | 用途 |
| --- | --- |
| `GET /api/admin/clients/{id}/owner-transfer` | 单设备预览；共享凭证时仍返回预览，但 `canTransfer=false` |
| `POST /api/admin/clients/{id}/owner-transfer` | 只接受 `scope=single` |
| `GET /api/admin/client-credentials/{id}/owner-transfer` | 完整凭证组预览，允许设备清单为空 |
| `POST /api/admin/client-credentials/{id}/owner-transfer` | 只接受 `scope=credential-group`，表示已显式确认整组 |

接口均要求管理员。非管理员 `403`；不存在或不属于调用者租户的路径资源统一 `404 RESOURCE_NOT_FOUND`。不先做跨租户查询再返回可识别的错误。

预览响应字段如下。ID 沿用现有管理 API 的 JSON 整数与安全整数约束；缺少值用 `null`，不能以 `0` 代替。

```json
{
  "scope": "single",
  "clientId": 1001,
  "credentialId": 501,
  "credentialOwnerUsername": "alice",
  "credentialEnabled": true,
  "affectedClients": [
    {"id": 1001, "clientName": "laptop", "ownerUsername": "alice", "enabled": true}
  ],
  "affectedClientCount": 1,
  "canTransfer": true,
  "conflictCode": null,
  "revision": "opaque-preview-revision",
  "accessRetained": true
}
```

凭证组预览的 `scope` 为 `credential-group`，`clientId=null`。无凭证的客户端预览中三个 `credential*` 字段均为 `null`。共享凭证的单设备预览展示完整关联清单，`canTransfer=false`、`conflictCode=CREDENTIAL_SHARED`、`revision=null`；前端必须切换到凭证组入口重新预览，不能把一次单设备操作改成组操作重试。预览不返回 secret、secret hash、客户端访问 token、设备私钥或机器指纹。

提交请求：

```json
{"scope":"credential-group","targetUsername":"bob","expectedRevision":"opaque-preview-revision"}
```

成功提交要求三个字段都存在且非空，类型或 scope 不符为 `400 INVALID_TRANSFER_REQUEST`；共享凭证冲突与缺少字段同时出现时，按下文顺序判定。服务端不接收客户端提供的设备清单作为转移依据。revision 是服务端生成的不透明一致性校验值，不是授权凭证；前端只能原样回传，不得解析。支持集群的实现中，由实例 A 生成的 revision 必须能由同数据库的实例 B 校验。

校验值必须绑定租户、scope、路径资源、关联凭证 ID 与其归属/启用状态，以及完整关联关系和各受影响客户端及 Peer 设备的归属/启用状态；重命名也使预览失效。在线状态、心跳、流量与 identity 的 last-seen 更新不应使预览失效。不同语言不要求生成相同字符串，但必须满足相同失效与集群校验语义。

服务端在写事务内重读并锁定范围、校验 revision 与目标账号当前状态。路径资源已经删除或不属于当前租户时，返回 `404 RESOURCE_NOT_FOUND`，即使请求带旧 revision 也不例外。当前关联已损坏、无法安全构建清单时为 `409 INCONSISTENT_CREDENTIAL_GROUP`。当前清单仍完整，但预览之后新增/删除关联设备、改名、变更归属或停用范围内资源时，为 `409 TRANSFER_PREVIEW_CHANGED`，零改动；管理员必须重新预览并确认。单设备请求遇到共享凭证返回 `409 CREDENTIAL_SHARED`，不能因请求遗漏 revision 而执行转移。冲突响应至少有 `error` 与稳定的 `code`，文案可本地化，前端不得按错误文本分支。

POST 校验顺序固定，后面的错误不覆盖前面的错误：

1. 解析管理身份与管理员权限，沿用既有认证失败响应；已认证非管理员 `403`。
2. JSON 不是对象、ID 格式非法：`400 INVALID_TRANSFER_REQUEST`。
3. 同租户路径资源不存在：`404 RESOURCE_NOT_FOUND`。
4. scope 缺失/不匹配，或已提供的 targetUsername/expectedRevision 不是字符串：`400 INVALID_TRANSFER_REQUEST`。
5. 当前关联不完整：`409 INCONSISTENT_CREDENTIAL_GROUP`。
6. 单设备范围关联共享凭证：`409 CREDENTIAL_SHARED`，即使 targetUsername/expectedRevision 缺失或为空也不执行转移。
7. targetUsername/expectedRevision 缺失或为空：`400 INVALID_TRANSFER_REQUEST`。
8. revision 不匹配：`409 TRANSFER_PREVIEW_CHANGED`。
9. 目标账号当前不可用：`400 INVALID_TARGET_OWNER`。
10. 原子写入、审计并提交；失败回滚，不返回部分成功。

因此「删除关联客户端但留下损坏 identity」优先报关系不一致；「完整删除设备和它的 identity」报预览已变。GET 同样先判身份与同租户路径资源；不能安全构建清单时返回关系不一致，而不是不完整的成功预览。

成功 `200`：

```json
{"scope":"credential-group","targetUsername":"bob","credentialId":501,"affectedClientIds":[1001,1002],"changed":true,"accessRetained":true}
```

返回 ID 与实际转移范围一致。所有资源已归目标且 revision 有效时为零改动成功，`changed=false`；不重置开关或生成重复成功审计。客户端遇到超时不能声称失败并自动重复确认，应重读归属与清单；再次使用已经失效的旧 revision 必须拒绝。

## 4. 事务、认证竞争与运行时

客户端、凭证、Peer 设备归属与一次成功审计在同一事务中提交；审计记录租户、执行人、scope、路径资源、各旧所有者、目标登录名、凭证 ID、完整受影响客户端 ID，不记录密钥。任一写入或审计失败都回滚；不得在回滚之前断开连接、下发配置或清除缓存。

必须与同凭证的 HTTP 登录/新 identity 创建串行化。仅在转移函数加锁不够：登录可能已在事务外读到旧凭证对象。认证流程在同一数据库协调边界内重新读取凭证的当前归属和启用状态，然后创建 identity/客户端；不能在转移提交后用旧对象创建原所有者的客户端。进程内锁不足以保护 Java/Go/.NET 的多实例共享数据库；按支持的数据库使用事务锁、条件更新或等效的数据库协调。

普通客户端/凭证编辑与删除、identity 关联增删、相关 Peer 设备更新也必须参加同一协调边界，避免校验后改变范围或旧事务覆盖新归属。目标账号的停用、删除和后续可能增加的改名同样与提交串行化：转移提交时目标必须可用，不能只在事务开始读一次就假定一直可用。之后独立执行的停用遵循原有停用规则，不反向回滚已提交转移。

| 数据或能力 | 转移行为 |
| --- | --- |
| 客户端与关联凭证的 `owner_username` | 按第 2 节范围修改 |
| 同租户 `peer_mesh_device.owner_username` | 跟随对应客户端，不凭空创建设备或重新分配地址 |
| ID、clientName、tenant、identity、virtual IP、公钥、密钥、启用状态、在线数量限制 | 保留；成功更新资源的 `updated_at` |
| TCP 映射、HTTP route、客户端发布的 Peer 服务与出口策略 | 保留 ID、配置、开关及客户端引用；新所有者按当前管理权限访问 |
| Peer ACL/出口策略的 `owner_username` | 这是策略记录的管理归属，不等于设备归属；不自动转给目标。删除管理账号时的策略再归属仍按 management-accounts 7.1 节 |
| 管理账号、个人工作台、绘图、附件、审计执行人等历史字段 | 不转移、不改写。个人引用仍须通过当前资源可见性校验 |
| 客户端 access token、control/data 连接 | 不因转移而统一吊销或重连；仍受既有认证与生命周期规则约束 |

提交后清除相关所有者/设备/权限缓存，重新计算受影响租户的 roster、服务目录、发布端来源白名单与出口有效授权。基于旧的「同一所有者」而失去授权的 Peer 会话和出口流必须按既有撤销路径关闭；仍有显式有效授权的连接不能被当成安全交接而一律断开。明确授予新所有者的管理与同所有者 Peer 权限是归属变更的预期效果，不得因此扩大无关第三方的显式 ACL 或服务白名单。

REST、管理 WebSocket 的客户端消息发送与连接事件过滤必须按当前客户端归属判权，不能继续使用连接建立时缓存的旧客户端所有者。旧所有者失去基于旧归属的管理与订阅权限；若另有本租户管理员等独立权限，则仍按现有角色规则访问，不因转移被降级。源/目标已打开的页面应重新读快照；可关闭相关管理订阅促使重连，但这不是关闭设备接入会话。单靠关闭管理订阅不够：已消费 ticket 与连接登记之间的竞态仍需当前资源授权检查。跨实例也必须满足当前资源判权。

直接 Peer 撤销、配置投递和集群通知仍受既有网络与协调限制约束，不承诺隔离网络中的瞬时安全交接。实现必须记录通知失败并采用已有重试/重同步路径；不能把通知失败隐藏成已完成密钥撤销，也不能让新的管理请求继续按旧缓存授权。

## 5. 管理页面

账号删除遇到 `409` 时分别显示剩余客户端数与凭证数，提供「查看并转移客户端」与「查看并转移接入凭证」。不能只跳到客户端列表：零设备凭证也会阻止删除。

客户端与凭证详情仅管理员可见转移入口。流程为选择目标 → 展示影响清单、原归属、目标归属和第 1 节警示 → 显式确认。共享凭证冲突展示「此凭证还关联其他设备，不能只转移这一台」与整组入口；整组确认按钮写明「转移此凭证及 N 台设备」，N 为 0 也明确展示。不得默认勾选确认，不通过普通保存按钮提交。

409 后保持对话框与目标选择，重新展示最新清单并要求再次确认；不自动重试。成功后刷新客户端、凭证、Peer 与账号删除计数，保留到新归属的可定位入口。错误、加载状态与键盘焦点遵循现有管理端组件，不暴露凭证 secret。

## 6. 四端共同验收

经真实管理 API 在新库中执行，不以直接 SQL 更新模拟转移；SQL 仅用于建造确定性夹具和断言。至少覆盖：

1. 非管理员、跨租户资源、无效/停用目标，且失败零改动；目标登录名大小写规范化与默认租户内置管理员。
2. 无凭证旧客户端、单客户端独占凭证、共享凭证单设备 `409`、完整组转移、零设备凭证；停用设备与凭证不被启用。
3. 多个旧所有者、重复 identity 的清单去重；遗留不一致关系失败关闭，不触及外租户。
4. 预览后新增设备/完整删除设备/改名/变归属/停用，旧 revision `409 TRANSFER_PREVIEW_CHANGED`；删除路径资源 `404`，留下损坏 identity `409 INCONSISTENT_CREDENTIAL_GROUP`；组合错误按校验顺序判断。心跳与流量不使预览失效；多实例交叉预览/提交。
5. 最后一步写入与审计故障回滚，数据库、缓存、订阅和客户端连接均不提前变更；零改动重复成功不产生重复审计。
6. HTTP 登录/新设备创建、普通编辑/删除/关联变更、Peer 行更新及目标账号停用/删除与组转移确定性交错：转移后绝不产生旧所有者的新客户端，不被旧写入覆盖；目标状态具有有效的提交顺序。不依赖 sleep 或概率重复。
7. 旧 secret 可继续 HTTP 登录，旧有效 token 可继续 control/data 认证，ID/名字/地址不变；现有停用/过期检查仍拒绝。
8. 普通用户原所有者的 REST 与已开管理 WebSocket 失去被转移客户端权限；目标获取权限；管理员原所有者保留独立角色权限；其他租户同名账号不受影响；覆盖 ticket 消费/登记竞态和真实双实例。
9. 同所有者默认 Peer 权限失效时，目录和数据面同步撤销；显式有效 ACL 保留；新所有者的默认权限按当前规则生成。出口/服务白名单不被意外放宽。
10. 成功转走最后的客户端/凭证后，账号可删除；个人资料与历史审计未转给新所有者。UI 完整组清单、409 再确认、零设备凭证和保留接入能力警示。

客户端删除的独立清理场景继续使用 [`client-peer-deletion-v1.json`](../test-vectors/client-peer-deletion-v1.json)，不能以「转移成功」替代删除事务和回滚验收。
