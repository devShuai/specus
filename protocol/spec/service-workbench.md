# 服务工作台（v1）

管理前端的服务工作台把四样东西放在一页：**常用服务**（用户自己收藏的服务）、**待处理问题**（从已有状态推导出的、需要处理的情况）、**最近打开**（用户最近从控制台打开过的服务）和**统一发布入口**。它回答「我平时用哪些服务、现在哪里有已知问题、刚才打开过什么、要发布新服务从哪里开始」，不回答「服务现在能不能访问」。

关联 [issue #38](https://github.com/devShuai/specus/issues/38) 的待办「服务工作台：常用服务、待处理问题、最近访问及统一发布入口；在线不等于目标可达，不自行扫描所有内网服务；收藏及历史按登录身份隔离」，见 [docs/issues/product-followups.md](../../docs/issues/product-followups.md)。

本文多处引用的 [service-connectivity-check.md](service-connectivity-check.md)（对单条 HTTP route 的有界连通性检查）随 PR #135（分支 `feat/connectivity-check`）合入；在它合入之前，链接以该分支为准。

本文的「工作台」指管理前端（`apps/admin-web`）的页面，与三端 CLI 的「本机连接工作台」（[cli-usage.md](../../docs/cli-usage.md)）无关，两者不共享任何数据。

**状态：契约已定（第 16 节各项采用推荐默认），四个服务端与管理前端已实现（第 18 节）。** 共享向量 `protocol/test-vectors/service-workbench-v1.json` 由 `tools/protocol/generate_service_workbench_vectors.py` 生成。

## 1. 现状

### 1.1 管理前端

- **登录后的首页**是「概览」（`OverviewPanel`），默认面板为 `overview`；地址栏 hash 已经指向某个面板时进入该面板。概览只有指标：读取 `GET /api/admin/overview`、`/traffic?limit=120`、`/clients`，展示客户端数和在线数、连接成功率、代理连接数、流量图表和版本分布，外加一条「接入设备，发布第一个服务」横幅。页面上没有服务、问题或最近使用的内容。
- **服务分在三个面板**，各有各的列表接口和展示字段：

| 类型 | 面板与接口 | 展示的目标信息 | 打开 / 复制 | 状态 |
| --- | --- | --- | --- | --- |
| HTTP route | `HttpRoutesPanel`；`GET /api/admin/http-routes` | `targetBaseUrl` 原样展示 | 「打开」是 `<a href target="_blank" rel="noreferrer">`，地址为 `${location.origin}/http/{clientName}/{route}/`；「复制」复制同一地址 | 所属设备的在线/离线/状态未知；route 停用只体现在开关上 |
| TCP 映射 | `SpecusMappingsPanel`；`GET /api/admin/specus-mappings` | `listenPort` 和 `targetAddress:targetPort` | 无 | 无设备在线状态 |
| Peer 服务 | `PeerMeshServicesTab`；`GET /api/admin/peer-mesh/services`、`/service-sharing`、`/service-audit`，每 5 秒轮询 | `publishedAddress`；`targetHost`/`targetPort` 不在表格中，只出现在管理员的编辑表单里 | 「复制地址」仅在目录可用时可点；没有打开按钮 | `peerServiceAvailability`：目录可用、全局服务共享已关闭、服务配置未启用、尚无运行实例上报、发布实例已离线、服务目录已过期、发布实例尚未上报此服务、发布实例缺少可用地址；每行注明「目标连通性未检测」 |

- **发布入口**分散在三处：三个面板顶部各有一个内联表单。HTTP 发布默认受保护，公开发布要二次确认，创建后提示「已创建 · 待验证访问」；TCP 映射没有确认和后续提示；Peer 服务只有租户管理员能创建，创建后默认关闭。接入引导（`ClientOnboardingGuide`）按「下载 → 接入设备 → 启动 → 发布 HTTP 服务」的顺序给出链接。没有统一的发布入口。
- **浏览器存储**：管理 token 存在 `sessionStorage`，按标签页隔离；退出或 401 时清除 token，面板状态随组件卸载丢弃，hash 保留。`localStorage` 里的键都不按用户区分：主题、绘图偏好（包括 `diagram-recent-node-kinds`、`diagram-favorite-node-kinds`，记录的是绘图节点类型，不涉及服务）以及公共互传的若干键。issue #37 确立的规则是页面里的敏感内容不写入浏览器持久存储。
- **请求封装**（`api/client.ts` 的 `request`）不区分旧服务端的 `404`/`405`；只有互传额度查询把它们显示为「服务端不支持」。

### 1.2 管理身份

| 服务端 | token | 调用者的租户与用户名 | 主键与唯一性 | 改名 | 删除账号 |
| --- | --- | --- | --- | --- | --- |
| Java | HS256 JWT（另接受 OIDC bearer），无会话表 | `ManagementContextResolver` 每次请求按 token 重读账号；租户取账号记录；`username` 是登录名 | 主键是账号键（新账号为 UUID），登录名按租户唯一，比较时 `trim().toLowerCase(ROOT)` | 不支持 | 只删账号行，不级联 |
| Go | HS256 JWT | `requireAuth` 每次按 `sub` 查账号；租户取账号记录 | `username` 为主键，全局唯一，`LOWER()` 比较 | 不支持 | 只删账号行，不级联 |
| .NET | HS256 JWT（另接受已绑定账号的 OIDC bearer） | 每次请求重读账号；`ManagementContext` 提供租户、用户名、角色 | `username` 为主键，全局唯一，`ToLower()` 比较 | 不支持 | 只删账号行，不级联 |
| C | HS256 JWT | 自 #133（`8d082b2`）起与 Java 相同：每次请求和刷新都重读账号，账号必须存在、已启用且仍属 token 的租户；租户与角色取账号记录 | `username` 为主键，`lower()` 比较 | 不支持 | 只删账号行，不级联 |

共同点：没有数值用户 id；内置管理员来自配置，没有账号行；客户端的 `owner_username` 是创建者的用户名，按字符串精确比较。

**可见性**在四端一致：管理员看见本租户全部客户端；普通用户只看见 `tenant_id` 等于自己租户、并且 `owner_username` 等于自己用户名的客户端。HTTP route、TCP 映射和 Peer 服务跟随所属客户端可见；Peer 服务的增删改只允许管理员，普通用户读到的 `targetHost`/`targetPort` 被置空。对不存在或不可见对象的响应四端不一致（Java 多为 `400`，Go 为 `403`/`404`，.NET 为 `400`/`403`，C 为 `404`）。

### 1.3 已有存储

- **四个服务端都没有收藏、最近使用、偏好或界面状态的存储。** 唯一按用户保存的数据是绘图文档 `user_diagram_document`（`tenant_id` + `owner_username`，每人最多 100 份），可以作为新表的参照；它在删除账号时也不会被清理。
- 没有通用审计表。Peer 服务审计在 Java、Go、.NET 中是内存里最近 80 条，C 落在 SQLite 里，每租户保留 80 条。
- 建表方式：Java 用 Hibernate `ddl-auto: update` 加手写迁移器；Go 维护 SQLite/PostgreSQL/MySQL 三份 DDL 和 `ensureColumn`；.NET 是三个提供程序各自的 EF Core 迁移加启动时的幂等 SQL；C 在 `st_storage_init` 里 `CREATE TABLE IF NOT EXISTS`。都不使用外键。
- 对象 id：Java、Go、.NET 的 HTTP route、TCP 映射和 Peer 服务 id 由应用随机生成，范围在 JavaScript 安全整数之内；C 的 route 与映射用 `AUTOINCREMENT`。Java 删除客户端时不删除其 route 和映射行。
- C 的管理接口曾把每个客户端的 route、映射限制在 64 条，JSON 响应必须放进 32 KiB 缓冲区；现在与 Java 一样不限条数（#191），唯一的边界是单条 `NAT_CONTROL` 消息 1 MiB 的上限，超出的新增或启用在创建时即被拒绝。

### 1.4 「待处理问题」能用的现有状态

| 信号 | 保存位置 | 现有接口与字段 | v1 是否使用 |
| --- | --- | --- | --- |
| 设备在线 | 各实例内存 | `GET /api/admin/clients`：`online`、`connectedSinceMs` | 用。多实例时只反映本实例持有的连接，与客户端页今天的口径相同 |
| 设备、route、映射、Peer 服务的启用状态 | 数据库 | 各列表的 `enabled` | 用 |
| Peer 服务共享总开关 | 数据库 | `GET /api/admin/peer-mesh/service-sharing`：`deploymentEnabled`、`configuredEnabled` | 用 |
| Peer 服务运行实例 | 各实例内存，5 分钟过期 | `GET /api/admin/peer-mesh/services` 的 `instances[]`：`online`、`advertised`、`expiresAt`、`lastReportedAt` | 用 |

## 2. 范围与分工

| 部分 | 在哪里实现 | 说明 |
| --- | --- | --- |
| 常用服务（收藏） | **服务端接口**（第 5 节） | 按管理身份保存在服务端数据库 |
| 最近打开 | **服务端接口**（第 5 节） | 同上；只在用户显式打开时记录（第 9 节） |
| 待处理问题 | **只在前端** | 从前端已经读取的现有列表推导，规则见第 10 节和向量的 `problems` 一节；不新增接口，不探测 |
| 统一发布入口 | **只在前端** | 跳转到现有的三个发布表单，沿用它们的确认流程（第 11 节）；不新增接口 |
| 合并的服务列表 | **只在前端** | 把三个现有列表合在一页展示（第 12 节） |

不在 v1 范围内：任何形式的探测、扫描或发现（局域网、端口、mDNS），后台或周期检查，服务端的「问题」聚合接口，保存连通性检查结果，产品指标，管理员查看或清空他人的列表，与 CLI 本机工作台同步。

### 2.1 为什么收藏和最近打开放在服务端

issue 要求「收藏及历史按登录身份隔离」。比较过三种做法：

| 做法 | 问题 |
| --- | --- |
| `localStorage`，键名带用户名 | 按浏览器配置隔离，不按身份隔离：同一浏览器的下一个人打开开发者工具就能读到；退出登录后数据仍在；换浏览器或设备就没有了；用户想清空历史时，没有办法清掉他用过的其他浏览器里的那份。也与 issue #37「页面敏感内容不写入浏览器持久存储」的规则冲突 |
| `sessionStorage` 或只在内存 | 关掉标签页就没了，「最近」失去意义 |
| 服务端按 `tenantId + username` 保存 | 跟随身份，跨浏览器和设备一致；清空一次即全部清空；账号删除时可以一并删除。代价是一张小表和七个接口，四端各实现一次，已有 `user_diagram_document` 可以参照 |

结论：收藏和最近打开都保存在服务端。**管理前端不得把它们写入 `localStorage`、`sessionStorage` 或 IndexedDB**，只在内存里持有，退出或切换身份时丢弃。

### 2.2 为什么待处理问题不做成服务端接口

- 推导所需的全部输入已经由现有列表接口返回，并且这些接口已经按调用者的可见性过滤。
- 服务端能提供的也只是同一份数据：在线状态和 Peer 运行实例本来就在各实例内存里，聚合接口不会比列表接口知道得更多。
- 四端各实现一个聚合接口，换来的只是少几个请求。前端已有 `peerServiceAvailability` 这样的模型可以沿用。
- 规则固定在共享向量的 `problems` 一节，由管理前端的测试读取，不会因为写在前端就没有约束。

将来如果某个只有服务端知道的信号被持久化（例如端口绑定失败），应当作为字段加到现有列表接口上，而不是新增一个工作台聚合接口。

## 3. 身份与隔离

- **工作台身份**是 `(tenantId, username)`，取自服务端已认证的管理会话：
  - `tenantId` 取账号记录中的租户；
  - `username` 取账号记录中的规范写法，也就是 `GET /api/admin/me` 返回的 `username`（Java 为登录名，内置管理员为配置中的写法），**不使用登录时用户输入的写法**；
  - 路径、查询串和请求体里没有任何账号或租户字段，调用者无法指定另一个身份。
- **每次请求都要确认账号仍然存在、仍然启用**，并以账号记录中的当前角色判断管理员身份。四端的共用鉴权层今天都已经这样做（C 自 #133 起），工作台接口沿用它，拒绝时的状态码也沿用各端现状（Java 与 C 对请求返回 `403`），向量里记作 `sessionRejected`，只断言不是 `2xx` 且没有写入。这一条不能省：已删除账号的旧 token 如果还能写入，就会把行写回去，之后同名重建的账号会继承这些行（向量 `account-deletion-cascades`）。
- 四个服务端都保证同一租户内不会出现只有大小写不同的两个账号（Java 按租户唯一，其余全局唯一），所以按规范写法精确比较即可，不会把两个账号混在一起。
- **没有任何接口可以读取、修改或清空别人的列表，管理员也不行。** 不提供导出。
- **账号删除时，删除该身份的全部工作台行**，与删除账号行在同一事务中完成，或者先删工作台行。现有实现删除账号时不清理其他数据（绘图文档、客户端所有权），工作台行不能照此处理：最近打开是个人历史，同名重建的账号不能看到。租户删除（如果实现了）同样删除该租户的全部行。
- 四端都不支持改名。将来支持时，行必须随账号一起改名，在同一事务中完成。
- **增长操作要求对象此刻对调用者可见**（添加收藏、记录打开），规则与该类型的列表接口相同：同租户，并且是管理员或所属客户端的所有者。**读取和删除从不检查可见性**：失去权限之后，用户仍然要能看到并删掉自己留下的引用（向量 `removal-needs-no-visibility`）。

## 4. 数据模型

### 4.1 服务引用

工作台只保存**服务引用** `(kind, id)`：

| `kind` | `id` 的来源 | 对应列表接口 |
| --- | --- | --- |
| `http-route` | `PUT/DELETE /api/admin/http-routes/{id}` 中的 `id` | `GET /api/admin/http-routes` |
| `tcp-mapping` | `PUT/DELETE /api/admin/specus-mappings/{id}` 中的 `id` | `GET /api/admin/specus-mappings` |
| `peer-service` | `PUT/DELETE /api/admin/peer-mesh/services/{id}` 中的数值 `id`（不是 `serviceId`） | `GET /api/admin/peer-mesh/services` |

- `kind` 的集合是封闭的，上表的顺序也是排序时打破平局的固定顺序。
- `id` 是 1..2^53−1 的整数，与现有 id 的范围一致，浏览器能精确表示。
- 设备本身、Peer ACL、出口策略等不是服务，不能收藏。

### 4.2 存储

每一行只有以下内容：

| 列 | 说明 |
| --- | --- |
| `tenant_id`、`username` | 工作台身份 |
| `list` | `favorite` 或 `recent` |
| `kind`、`object_id` | 服务引用 |
| `at_ms` | 收藏为加入时刻，最近打开为最近一次打开的时刻；服务端时钟，毫秒精度 |

- 唯一键 `(tenant_id, username, list, kind, object_id)`；为级联删除建索引 `(tenant_id, kind, object_id)`，为保留期清理建索引 `(list, at_ms)`。建议表名 `management_workbench_item`。
- 时间必须保存到毫秒，排序依赖它。建议用 BIGINT 保存 epoch 毫秒；如果沿用现有的字符串时间，必须是定长、带三位小数的 UTC 格式，使字典序等于时间序。
- **不保存**：服务名称、目标地址、访问地址、端口、客户端名称、调用者 IP、User-Agent、打开次数、停留时长、访问是否成功。
- 不建外键，与现有表一致。

## 5. 接口

| 方法 | 路径 | 作用 | 限流 |
| --- | --- | --- | --- |
| `GET` | `/api/admin/workbench` | 读取自己的两张列表 | 否 |
| `PUT` | `/api/admin/workbench/favorites/{kind}/{id}` | 加入收藏，幂等 | 是 |
| `DELETE` | `/api/admin/workbench/favorites/{kind}/{id}` | 取消一项收藏，幂等 | 否 |
| `DELETE` | `/api/admin/workbench/favorites` | 清空收藏 | 否 |
| `POST` | `/api/admin/workbench/recents/{kind}/{id}` | 记录一次打开 | 是 |
| `DELETE` | `/api/admin/workbench/recents/{kind}/{id}` | 删除一条最近打开，幂等 | 否 |
| `DELETE` | `/api/admin/workbench/recents` | 清空最近打开 | 否 |

### 5.1 请求

- 鉴权与其他 `/api/admin` 接口相同（`Authorization: Bearer`）。管理 token 不在 cookie 里，跨站请求带不上它。
- 没有查询参数；**不读取请求体**。
- `{kind}` 必须与 4.1 的名称逐字相同，区分大小写。
- `{id}` 必须是十进制 ASCII 数字，不带符号、空白或前导零，值在 1..2^53−1。实现要按字符串取出再校验：例如 Spring 把 `042` 绑定成 `Long` 时会得到 `42`，这样的请求必须拒绝。

### 5.2 处理顺序与状态码

| 顺序 | 情形 | HTTP | `code` |
| ---: | --- | ---: | --- |
| 1 | 没有有效的管理会话 | `401` | — |
| 1 | token 有效，但账号已不存在、已停用 | 沿用共用鉴权层的现状（`401` 或 `403`） | — |
| 2 | `kind` 或 `id` 非法 | `400` | `WORKBENCH_REQUEST_INVALID` |
| 3 | 仅增长操作：该身份的限流拒绝（第 7 节） | `429` | `WORKBENCH_RATE_LIMITED` |
| 4 | 存储无法读取或写入 | `503` | `WORKBENCH_UNAVAILABLE` |
| 5 | 仅增长操作：对象不存在，或此刻对调用者不可见 | `404` | `WORKBENCH_TARGET_NOT_FOUND` |
| 6 | 仅加入收藏：该引用不在收藏中，且已有 50 项 | `409` | `WORKBENCH_FAVORITES_FULL` |
| 7 | 成功 | `200` | 响应体为完整文档 |

- 前面任何一步拒绝时，后面的步骤都不执行。
- 错误响应体为 `{"code": "<上表的 code>"}`，可以附带现有管理接口惯用的 `error` 文本；向量只比较 `code`。`429` 带 `Retry-After`（整秒，向上取整，至少 1）。
- **存储读失败不得报成空列表**，否则后端故障会被显示成「没有收藏」。
- 对象不存在、属于其他租户、属于别的所有者，响应完全相同，都是 `404`。服务端不提供某一类服务时（例如部署里没有任何 Peer 服务），增长操作同样是 `404`；接口不透露某类服务是否被支持。
- 所有响应都带 `Cache-Control: private, no-store`。
- 成功的写操作也返回 `200` 和完整文档，不返回 `204`：页面直接用服务端的结果替换本地状态，不再自己推算。
- 旧服务端对 `GET /api/admin/workbench` 返回 `404` 或 `405`。前端应显示「当前服务端不支持保存常用服务与最近打开」，隐藏收藏和最近打开，不能当作两张空列表。

### 5.3 响应

```json
{
  "schemaVersion": 1,
  "limits": {"maxFavorites": 50, "maxRecents": 20, "recentRetentionDays": 30},
  "favorites": [
    {"kind": "http-route", "id": 42, "addedAt": "2026-10-06T08:00:00.123Z"},
    {"kind": "peer-service", "id": 7, "addedAt": "2026-10-06T08:05:00.000Z"}
  ],
  "recents": [
    {"kind": "tcp-mapping", "id": 9, "visitedAt": "2026-10-06T09:12:30.456Z"}
  ]
}
```

- 时间是 UTC RFC 3339，**固定三位小数**。
- 引用只有 `kind`、`id` 和时间，没有名称或地址。页面用已经读到的列表把引用解析成服务（第 12 节），因此展示的内容不会超出用户在各列表里本来就能看到的范围。
- 整份文档最多 70 项，约 6 KiB，放得进 C 的 32 KiB 响应缓冲区。

### 5.4 各操作的语义

- **读取**：返回全部收藏（按 6.2 排序），以及保留期内、排序后的前 20 条最近打开。**读取从不写入**，过期或超限的行在读取时只被过滤，不被删除；因此打开或刷新页面不会改动任何数据。
- **加入收藏**：先判断可见性（第 5 步）；引用已经在收藏中时不做任何改动，`addedAt` 也不变，即使收藏已满也返回 `200`；否则在已有 50 项时返回 `409`，不淘汰任何一项；不满时以当前时刻加入。
- **记录打开**：先判断可见性；然后以 `visitedAt = max(已存时刻, now)` 写入或更新这一条。同一服务只占一条，再次打开会把它移到最前面。
- **删除与清空**：不判断可见性，引用不存在时照样返回 `200`。只作用于调用者自己的行。
- **每次成功的写操作**（包括删除和清空）之后，整理调用者自己的最近打开：删除过期的行，再删除排在第 20 条之后的行。
- **对象被删除时**（经现有的 route、映射、Peer 服务删除接口，或者删除承载它们的客户端），删除**所有身份**对该对象的引用，与删除对象在同一事务中完成，或者先删引用。Java 删除客户端时会留下 route 和映射行，但它们的引用同样要删除。这样，即使 id 以后再次出现（随机 id 碰撞、从备份恢复），新对象也不会继承旧引用（向量 `object-deletion-cascades`）。
- **对象换了所有者**（今天没有接口可以修改 `owner_username`，但数据可能被直接修改或来自旧版本）时，旧所有者的引用保留：它仍然出现在文档里，但在旧所有者能读到的列表里已经解析不到，也不能再加入；用户可以删除它。

## 6. 上限、排序与时间

### 6.1 上限

| 项 | 值 | 超出时 |
| --- | ---: | --- |
| 每个身份的收藏数 | 50 | 加入新的一项返回 `409 WORKBENCH_FAVORITES_FULL`，不自动淘汰：收藏是用户的明确选择，悄悄删掉一项比拒绝更糟 |
| 每个身份的最近打开 | 20 | 淘汰最旧的一条，被淘汰的行被删除而不是隐藏：最近打开是自动产生的记录 |
| 最近打开的保留期 | 30 天 | `now − visitedAt < 30 天` 时可见（严格小于，恰好 30 天即过期）。过期的行由该身份的下一次写操作删除，并由全局清理在过期后 24 小时内删除 |
| 收藏的保留期 | 无 | 只在用户删除、对象删除或账号删除时消失 |
| `id` | 1..2^53−1 | `400` |

这些值在 v1 中固定，不做成配置项；向量固定了它们。

### 6.2 排序

- 收藏按 `addedAt` **升序**：新加入的排在最后，已有各项的位置保持不变。
- 最近打开按 `visitedAt` **降序**。
- 时间相同时按 `kind` 的固定顺序（`http-route`、`tcp-mapping`、`peer-service`），再按 `id` 升序。

v1 不支持手动调整收藏顺序。

### 6.3 时间

- 所有时间都取服务端时钟，精确到毫秒。不接受客户端提供的时间。
- 多实例的时钟可能有偏差。同一条引用的时间只进不退（`max` 规则，向量 `clock-behind-never-moves-a-visit-back`）；不同引用之间的先后可能因时钟偏差而略有出入，部署应当对时。

## 7. 限流

- 增长操作（加入收藏、记录打开）共用一个键 `tenantId + username`，用 GCRA：`interval = 1000 ms`，`burst = 30`，容差 `(burst − 1) × interval`。规则与 [service-connectivity-check.md](service-connectivity-check.md) 第 7 节的 GCRA 相同。
- 被拒的请求不消耗额度；放行的请求即使随后得到 `404`、`409` 或 `503`，也消耗额度。`400` 在限流之前判断，不消耗。
- **删除和清空永远不限流**：用户清理自己的历史不能被挡住。它们只会让数据变少，行数又有上限。
- 状态在进程内存里，与现有限流器一致，多实例部署下按实例计算。键数上限 10 000：TAT 不晚于 `now` 的条目等同于不存在，可以随时淘汰；全部条目仍然有效而又要新增键时，该请求按 `429` 拒绝，`Retry-After: 1`。
- 限流的作用是保护数据库：一个出错的页面或泄露的 token 不能用写请求把库刷满。数据量本身已经被上限约束。

## 8. 多实例与并发

- Java、Go、.NET 的多实例部署共用一个数据库（MySQL 或 PostgreSQL）；默认的 SQLite 和 C 的本地 SQLite 只有一个实例。工作台数据都在数据库里，**不在内存中缓存**，因此从任何一个实例读到的列表都相同。
- **收藏的上限在并发下也要成立**：加入收藏要按身份串行化。SQLite 只有一个写者，天然满足；MySQL、PostgreSQL 可以在事务里锁住该身份的行（`SELECT … FOR UPDATE`）或用等价手段。做不到串行化的实现允许因竞争而多出一项，此时读取照样返回全部收藏（明确的选择不能被藏起来），加入收藏持续返回 `409`，直到数量低于上限（向量 `favorites-overflow-is-shown`）。
- **最近打开**的并发写入可能让行数暂时超过 20：读取只返回前 20 条，下一次写操作删除多余的行（向量 `recents-over-bound-rows`）。
- 同一条引用的并发写入依靠唯一键加 upsert 完成，例如 `INSERT … ON CONFLICT … DO UPDATE SET at_ms = max(at_ms, excluded.at_ms)`。
- 全局保留期清理可以在任一实例上运行，至少每 24 小时一次；它是幂等的 `DELETE … WHERE list = 'recent' AND at_ms <= now − 30 天`，多个实例同时运行也没有问题。
- 限流按实例计算（第 7 节）。
- 待处理问题依赖的在线状态和 Peer 运行实例在各实例内存里：管理请求落到不持有该设备连接的实例时，会看到设备离线。这与客户端页今天的口径相同，是已知限制（第 16 节）。

## 9. 什么算一次「打开」

「最近打开」记录的是**用户在管理前端里显式打开或复制某个服务的访问方式**，不是访问日志，也不说明访问是否成功。界面名称用「最近打开」而不是「最近访问」，避免让人以为服务端确认过访问（第 16 节）。

只有以下动作会记录（封闭列表）：

| 类型 | 记录的动作 |
| --- | --- |
| HTTP route | 用鼠标左键或中键点击访问链接「打开」；点击「复制访问链接」 |
| TCP 映射 | 点击「复制公网端口」（第 16 节） |
| Peer 服务 | 点击「复制地址」；对 HTTP(S) 服务点击「打开」（地址按 [peer-mesh.md](peer-mesh.md) 由 `virtualIp + publishedPort + 安全 path` 构造） |

以下情况**一律不记录**：页面加载、刷新、轮询、列表渲染、切换标签页或面板、展开详情、悬停或键盘聚焦、新建、编辑、启停或删除服务、点击收藏、连通性检查、「检查目录状态」，以及通过浏览器右键菜单复制链接（页面无法可靠察觉）。

- 先完成动作，再发记录请求：「打开」仍然是原生链接，不改成 `window.open`，也不等待记录请求完成。记录请求用带 `Authorization` 头的 `fetch(…, {keepalive: true})`；`navigator.sendBeacon` 无法携带 bearer，不能用。
- 记录失败（包括 `429`、`503` 和旧服务端的 `404`/`405`）静默忽略：不弹提示，不重试，不影响打开。成功时用响应里的文档更新「最近打开」。
- 只有管理前端里的动作才算。用户在别处访问公网地址不会被记录；**服务端不得从流量明细、连接记录或任何日志推导最近打开**。

## 10. 待处理问题（只在前端）

### 10.1 输入

只用前端已经读取的五个接口：`GET /api/admin/clients`、`/http-routes`、`/specus-mappings`、`/peer-mesh/service-sharing`、`/peer-mesh/services`。不新增请求类型，不发起任何探测、连通性检查、目录检查、mDNS 导入或扫描。进入工作台和点击「刷新」时读取；页面可见时最多每 30 秒重读一次，页面隐藏时不读。

每个来源的读取结果分三种：`ok`；`failed`（网络错误、`5xx`、畸形响应）；`unsupported`（`404`/`405`，服务端没有这类服务，例如旧服务端或部署不提供 Peer 服务）。

### 10.2 规则

只看**已启用**的服务；停用是用户的选择，不是问题。每个服务按下表从上到下取**第一条**命中的规则，只出现在一个问题里：

| 顺序 | `code` | 级别 | 条件 | 标题 | 下一步 |
| ---: | --- | --- | --- | --- | --- |
| 1 | `DEVICE_DISABLED` | blocking | 所属设备已停用 | 设备已停用，其上 N 个已启用的服务不会对外提供 | 启用该设备，或停用这些服务；普通用户请联系租户管理员 |
| 2 | `DEVICE_OFFLINE` | blocking | 所属设备离线 | 设备离线，其上 N 个已启用的服务现在无法经 specus 访问 | 启动该设备上的客户端，或检查它到服务端的网络 |
| 3 | `PEER_SHARING_OFF` | blocking | Peer 服务，且部署未启用 Peer Mesh 或租户服务共享总开关关闭 | 服务共享已关闭，N 个已启用的 Peer 服务不会出现在任何对端的目录中 | 租户管理员在「Peer 服务」中开启服务共享 |
| 4 | `PEER_NOT_REPORTED` | attention | Peer 服务，没有运行实例，或运行实例已离线 | 发布设备还没有上报这些服务 | 发布端只在存在获授权的在线对端时才探测和上报；如果有对端在线，确认设备上的目标服务已启动 |
| 5 | `PEER_DIRECTORY_EXPIRED` | attention | Peer 服务，运行实例在线但目录已过期 | 服务目录已过期 | 发布设备可能停止了上报；稍后刷新，持续出现时检查该设备的客户端 |
| 6 | `PEER_NOT_ADVERTISED` | attention | Peer 服务，运行实例在线、目录未过期，但没有包含此服务或缺少可用地址 | 发布设备在线，但没有发布这些服务 | 发布端本机探测没有成功：确认目标服务已启动并在配置的端口上监听 |

- **blocking** 表示从状态就能确定此刻无法经 specus 使用这些服务：离线或停用的设备一定无法承载访问。**attention** 表示目录里没有这项服务，但原因从状态上定不下来，措辞必须说明「原因未定」，不能断言目标服务坏了。
- 第 4–6 条沿用 `peerServiceAvailability` 的判断次序。
- 分组：第 1、2、4、5、6 条按设备分组，第 3 条整个租户一组。排序：blocking 在前，然后按上表顺序，再按设备 id 升序。组内服务按 `kind` 的固定顺序再按 `id` 排序。
- 设备列表读取成功、但其中找不到某个服务的设备（两次读取之间的竞争）时，该服务不报离线。
- **任何来源读取失败时，问题列表标为「不完整」**，并列出未能读取的来源；能推导的问题照常列出。读取失败绝不能显示成「没有问题」。`unsupported` 不算失败。
- 连通性检查的结果不进入问题列表：它没有被保存，只显示在检查过的那条 route 旁边（[service-connectivity-check.md](service-connectivity-check.md) 第 10 节），刷新后消失。

### 10.3 措辞：在线不等于可达

1. 不得根据状态说「正常」「健康」「可用」「可访问」「已连通」，也不用绿色对勾。
2. 没有问题时只能说「未发现已知问题」，并且必须紧跟一句「这不代表服务可以访问；需要确认时，请对单个 HTTP 服务做连接检查」（连接检查上线之前改为「请手动打开访问链接验证」）。
3. 设备在线在页面上第一次出现时写作「设备在线（不代表目标服务可访问）」。
4. 设备离线可以写「无法经 specus 访问」：这个方向是确定的。
5. Peer 服务沿用现有措辞：「目录可用」「目标连通性未检测」。
6. 问题列表标明「状态读取于 hh:mm:ss」（浏览器时间）；距上次成功读取超过 60 秒时标「已过时」。
7. 多实例部署时，「设备离线」可能是请求落到了不持有该设备连接的实例；问题说明里注明这一点。

## 11. 统一发布入口（只在前端）

- 工作台上放一个「发布服务」按钮，打开选择框，列出三种服务及其适用场景：HTTP 网页服务、TCP 端口、Peer 内网服务。选择后跳转到对应的现有表单（`#/http-routes`、`#/specusMappings`、Peer 服务标签页）。
- **沿用现有表单和它们的全部确认**：HTTP 默认受保护，公开发布要再次确认；Peer 服务只有管理员能创建，创建后默认关闭。入口本身不调用任何写接口，不提供批量发布或一键发布。
- 入口**不推荐服务**：不扫描、不探测、不触发 mDNS 或 TCP/HTTP 候选导入。管理员仍然可以在 Peer 服务标签页里显式使用现有的导入功能。
- 还没有设备时先引导去接入（`#/clients`）；设备列表读取失败时说明「设备状态读取失败」，不能当作没有设备（issue #37 的规则）。
- 不可用的选项要说明原因并禁用：普通用户的 Peer 服务（「需要租户管理员」），Peer 服务接口返回 `404`/`405` 或部署未启用 Peer Mesh。
- 创建成功后沿用「已创建 · 待验证访问」的提示。发布入口不会自动收藏，也不会记录一次打开。

## 12. 工作台页面

- 新增面板 `#/workbench`。
- **合并的服务列表**：把三个列表合在一页，每行只展示该服务在原面板里本来就展示的字段，加上收藏开关、打开或复制操作，以及待处理问题的标记。
- **引用的解析**：收藏和最近打开里的每条引用，用已经读到的列表按 `(kind, id)` 查找。找不到时显示为「不在当前可见列表中」，说明可能已被删除、权限已变化、列表被截断（C 每页 64 条），或该列表读取失败，并提供删除按钮。**不得从别处补出名称或地址。**
- 收藏和最近打开只保存在内存：退出、401 或 `GET /api/admin/me` 返回的身份变化时清空；发出请求之后身份发生变化，迟到的响应一律丢弃。
- 工作台文档读取失败时显示「读取失败」，不显示成空列表；旧服务端见 5.2。
- 「清空最近打开」一步完成，不需要确认：清理隐私数据应当容易。「清空收藏」需要确认：收藏是用户的明确选择。
- 页面加载只发 `GET`，不发任何写请求。

## 13. 隐私

- 服务端只保存服务引用和时间（4.2），不保存任何能单独说明服务内容或访问情况的信息。
- 页面展示的内容不超过用户在各列表里本来就能看到的范围；失去权限之后，旧引用只剩 `kind` 和 `id`。
- 最近打开保留 30 天，收藏保留到用户删除为止；对象删除和账号删除时一并删除；用户可以逐项删除或一次清空。
- **日志**：成功的工作台操作不写日志，不能借此形成访问日志。失败只记录 `[workbench] tenant=<tenantId> user=<username> op=<操作> code=<code>`，不写 `kind`、`id`、对象名称或目标。
- 工作台数据不用于产品指标（issue #38 的另一项待办），不做跨用户的聚合，不提供管理员视图或导出。

## 14. 共享向量

`protocol/test-vectors/service-workbench-v1.json` 由 `python tools/protocol/generate_service_workbench_vectors.py` 生成。生成器内置参考实现，写文件之前用手写的期望表逐条断言每一步的结果，另外断言：

- 每个 `200` 文档的收藏按 6.2 排序、最近打开按 6.2 排序，没有重复引用，最近打开不超过 20 条，不包含过期条目，引用只有 `kind`、`id` 和时间；
- 每个场景结束后存储里剩下的行与手写的 `rowsAfter` 一致，证明过期、超限和级联删除的行被真正删除；剩下的每一行都属于仍然存在的身份和对象；
- 5.2 的每一种拒绝都至少出现一次，并且更早的拒绝会遮住更晚的拒绝；
- `problems` 一节的每个问题码至少被一条用例覆盖，每个服务最多出现在一个问题里，blocking 排在 attention 之前。

**服务端如何使用。** 每个 `scenario` 独立运行：

1. 按 `users` 建账号（`admin` 为租户管理员），按 `objects` 建对象（`ownerUsername` 是所属客户端的 `owner_username`），把 `rows` 直接写入工作台表（可以超出上限，用来模拟竞争留下的行），限流器从空开始。
2. 按顺序重放 `steps`。带 `method`/`path` 的一步通过真实的 HTTP 处理代码调用接口，`as` 是已认证的身份（`null` 表示没有会话），时钟固定在 `baseTime + atMs`；断言 `expect` 的 `httpStatus`、`retryAfterSeconds`（对应 `Retry-After`）以及 `body`（错误时只比较 `code`），时间按时刻比较。`expect` 为 `{"sessionRejected": true}` 时，`as` 指向已删除的账号：用删除之前签发的 token 调用，断言共用鉴权层拒绝（不是 `2xx`）且没有写入任何行。
3. 带 `event` 的一步不是工作台接口：`delete-object` 走现有的删除路径；`set-admin`、`create-user`、`delete-user` 走现有的账号管理；`change-owner` 由测试夹具直接修改数据；`store-down`/`store-up` 由测试让存储读写失败或恢复；`sweep` 触发一次全局保留期清理。
4. 场景结束后，读出工作台表的全部行，与 `rowsAfter` 逐行相等。

只断言「语义相近」不算通过。

**管理前端如何使用。** `problems.cases` 的 `input` 是前端从五个列表接口读到的状态（已经抽象成 `enabled`、`online`、运行实例的 `online`/`expired`/`advertised`/`hasAddress`），`expect` 是待处理问题列表；前端测试把同一输入交给真实的推导函数，逐字段比较。

## 15. 放弃的方案

| 方案 | 不采用的原因 |
| --- | --- |
| 收藏或最近打开存在 `localStorage`（键名带用户名） | 见 2.1：按浏览器隔离而不是按身份，共用浏览器时泄露，退出后残留，无法跨设备，也无法一次清空 |
| 服务端读取时联表，返回服务名称和地址 | 读取路径要依赖三类服务的模块；对已经失去权限的对象返回名称会泄露；还会把响应撑大（C 的 32 KiB 缓冲区）。前端本来就要读这些列表 |
| 读取时过滤掉已不可见的引用 | 用户就看不到也删不掉这些引用，只能等它们永远留在库里 |
| 按打开次数自动生成「常用服务」 | 需要保存次数，形成使用画像；常用服务只由用户显式收藏 |
| 从流量明细、连接记录推导最近访问 | 这是监控而不是用户自己的历史，而且在默认关闭明细采集时并不准确 |
| 收藏满了自动淘汰最旧的一项 | 悄悄删除用户的明确选择 |
| 服务端提供「问题」聚合接口 | 见 2.2 |
| 把连通性检查结果当作待处理问题 | 检查结果不保存；保存「上次检查」会被当作当前状态，见连通性检查契约第 8 节 |
| 后台或周期探测，显示「健康」 | issue 明确要求不自行扫描内网服务；在线不等于可达 |
| 记录打开时在请求体里传 JSON | 路径已经完整表达引用；不读请求体，各端就没有 JSON 解析差异 |
| 删除返回 `204` | 页面需要服务端整理之后的权威列表 |

## 16. 已定事项（采用推荐默认）

以下各项在草案阶段列为待定，按维护者对同类问题的一贯做法，采用各条的推荐默认。

1. **登录后的默认页面是否改为工作台？** 推荐：是，对所有用户；「概览」保留在导航中。工作台回答「我要做什么」，概览回答「整体运行得怎样」。
2. **上限与保留期是否可配置？** 推荐：不可配置，固定为 50 / 20 / 30 天；向量固定这些值。
3. **「复制地址」算不算一次打开？** 推荐：算。对 TCP 和 SSH 类服务，复制地址就是打开它的方式。
4. **TCP 映射复制什么？** 现有接口没有映射的公网主机名，数据面主机也可能不同于管理页的域名。推荐：v1 只提供「复制公网端口」并记作一次打开；公网主机名以后由服务端配置提供，不在前端猜。
5. **界面叫「最近打开」还是「最近访问」？** 推荐：「最近打开」，它记录的是从控制台打开的动作，不是访问结果；issue 的「最近访问」指同一能力。
6. **账号停用时是否删除工作台数据？** 推荐：不删除，只在删除账号时删除；停用的账号调不了接口，重新启用后列表恢复。
7. **对象换了所有者时，是否主动删除旧所有者的引用？** 推荐：不主动删除，由旧所有者自己删除（5.4）；今天也没有修改所有者的接口。
8. **多实例下「设备离线」可能误报，是否改用数据库里的会话状态？** 推荐：v1 不改，与客户端页保持同一口径并在说明中注明；之后对在线状态单独立项，同时修正客户端页。
9. **虚拟网卡错误、设备未启用私有组网是否列为问题？** 推荐：v1 不列。它们影响的是 Peer Mesh 设备本身，已经在组网页展示；工作台先只覆盖第 10 节的六条规则。
10. **收藏是否支持手动排序？** 推荐：v1 不支持，按加入顺序排列。

## 17. 附带发现

调研中发现以下问题，不属于本契约，需要另行处理：

- C 的管理账号修改和删除（`PUT/DELETE /api/admin/users/{username}`）没有校验租户，SQL 只按用户名过滤；用户名又是全局唯一的，所以任一租户的管理员可以修改或删除其他租户的账号。Java、Go、.NET 都会拒绝跨租户目标。
- 删除账号时，四端都不清理该账号的客户端所有权和绘图文档；以同名重建的账号会继承它们。
